# Happy Horse: изображение и видео через MCP

Начальный source-bound срез трёх моделей. Для каждого режима получено одно
реальное видео через MCP; это проверка отдельных начальных сценариев.
Это не полный набор настроек интерфейса и не гарантия доступа на любом тарифе.

## Включение

```sh
node scripts/print-media-mcp-config.mjs --confirm-enable-paid-tools --include-happy-horse
```

В напечатанном шаблоне замените `SYNTX_OWNER_HAPPY_HORSE_UPLOAD_DESTINATION`
одним выбором `uploaded` или `hidden`, а
`SYNTX_OWNER_HAPPY_HORSE_FFPROBE_PATH` — абсолютным путём к доверенному
`ffprobe`. Группа выключена по умолчанию; выключенный режим не требует этих
настроек. Печать шаблона не меняет клиент, не входит в аккаунт и не генерирует.
Проверьте общий шаблон и оставьте только нужные owner-группы.

## Начальные сценарии

| model_id | вход | file_urls type |
| --- | --- | --- |
| `happy_horse_first_frame` | одно изображение | `first_frame` |
| `happy_horse_references` | одно изображение | `image` |
| `happy_horse_edit` | одно измеренное видео, без изображений | `video` |

Явные начальные настройки для всех трёх: `aspect_ratio:"16:9"`,
`resolution:"720P"`, `video_duration:5`, `seed:null`, непустой prompt.
Эффективные значения других полей, включая звук, этим срезом не утверждаются.
Не включены несколько референсов, дополнительные изображения при edit,
остальные разрешения, длительности, соотношения сторон и seed-режимы.

Изображения: JPEG/PNG/WebP, до 10 MiB, стороны 400–8000 пикселей; локально
проверяются контейнерные метаданные, без автоматической обрезки. Видео:
MP4/MOV, до 100 MiB, стороны 400–2160; доверенный ffprobe измеряет поток.
Повторно используемый локальный probe ограничивает вход 30 секундами, хотя
публичные метаданные указывают до 60. Это консервативная локальная граница,
не новая спецификация провайдера. Путь к исполняемому файлу задаёт оператор,
не MCP-вызов.

Probe также требует известную SDR transfer-характеристику. Отсутствующее поле
`color_transfer` не считается подтверждённым SDR: такой вход отклоняется до
загрузки. Автоматического перекодирования или удаления HDR нет.

## Наблюдаемые результаты и ограничения

`references` и `edit` вернули MP4/H.264 1280×720, около пяти секунд; `first_frame`
с квадратным исходным изображением вернул 960×960 несмотря на запрос `16:9`.
Поэтому наличие результата не доказывает соблюдение aspect ratio. MCP не
обрезает вход и не исправляет выход автоматически. На других тарифах, входах
и сочетаниях настроек доступность и формат результата пока не проверены.

## Инструменты

После обычного Telegram-входа загрузите вход в
`syntx_owner_upload_happy_horse_image` либо
`syntx_owner_upload_happy_horse_edit_video`. Передайте полученный
`reference_handle` в `syntx_owner_generate_happy_horse_video` с тем же
`model_id`. URL загрузки не выводится. Каждый handle привязан к аккаунту,
связке, native-клиенту и сроку жизни текущего процесса.

Сервис дважды читает подписку, баланс и quote с ключами `resolution` и
`video_duration`: перед созданием собственного чата и перед одним POST.
Это проверка доступности средств, а не жёсткий лимит списания провайдера.
Готовый ответ возвращает проверенные ссылки на видео; для ожидания используйте
`syntx_owner_get_happy_horse_result`, а для локальных записей —
`syntx_owner_list_happy_horse_recoveries`.

При неизвестном upload/POST автоматическая повторная отправка запрещена.
Получение результата — только GET собственного чата и точного сообщения.
Recovery пока не переживает перезапуск; provider billing и полная UI-паритетность
не подтверждены синтетическим тестом.
