# Hailuo: изображение в видео через MCP

Начальный срез для трёх точных child ID. По одному результату `hailuo-2.3-fast`,
`hailuo-01-live-character` и `hailuo-3.0` подтверждено через MCP. Это три
начальных случая, а не подтверждение всех настроек или доступности каждого
варианта. `hailuo-minimax` — исключённый из текущего селектора корневой ID; он
не подменяется child-моделью.

## Включение

```sh
node scripts/print-media-mcp-config.mjs --confirm-enable-paid-tools --include-hailuo-initial
```

Замените `SYNTX_OWNER_HAILUO_INITIAL_UPLOAD_DESTINATION=<uploaded|hidden>`
одним явным выбором оператора. Группа выключена по умолчанию. Печать
конфигурации не меняет настройки клиента, не входит в аккаунт, не загружает
изображения и не запускает генерацию. В общем шаблоне есть и другие группы;
перед установкой оставьте только нужные.

## Поддерживаемые начальные сочетания

Каждый сценарий принимает одно принадлежащее текущей связке изображение:

| model_id | resolution | video_duration | дополнительные поля |
| --- | --- | --- | --- |
| `hailuo-2.3-fast` | `768p` | 6 или 10 | нет |
| `hailuo-2.3-fast` | `1080p` | 6 | нет |
| `hailuo-01-live-character` | `720p` | 6 | нет |
| `hailuo-3.0` | `2K` | 5 | `mode:"omni-references"`, `aspect_ratio:"16:9"` |

Регистр значений важен. Все поля задаются явно. Это ограниченный срез, а не
полный набор настроек формы. Для Hailuo 3.0 не включены два кадра, другие
длительности, видео- и аудиореференсы.

Локально принимаются JPEG, PNG и WebP, не более 10 MiB, с ограниченной
геометрией; проверяются контейнерные метаданные. Эти защитные пределы не
объявляются лимитами провайдера или полной проверкой декодированных пикселей.
Изображение не обрезается и не масштабируется автоматически.

## Порядок работы

1. Выполните обычный вход через `syntx_begin_login` и `syntx_check_login`.
2. Передайте файл в `syntx_owner_upload_hailuo_initial_image` и сохраните
   возвращённый `reference_handle`. URL загрузки не возвращается.
3. Вызовите `syntx_owner_generate_hailuo_initial_video` с тем же `model_id`,
   handle, явным prompt и сочетанием из таблицы.
4. Если результат ещё не подтверждён, используйте только
   `syntx_owner_get_hailuo_initial_result` с полученным `recovery_id`.
   `syntx_owner_list_hailuo_initial_recoveries` показывает локальные записи.

Генерация дважды проверяет актуальную связку, подписку, баланс и quote: до
создания чата и до отправки. Для Fast/Live используются ключи стоимости
`resolution`, `video_duration`; для Hailuo 3.0 — объявленные каталогом
`ref_count`, `resolution`, `duration`, `video_duration`. Значения `ref_count:1`
и `duration:5` для одиночного референса — начальное сопоставление, которое ещё
требует подтверждения живой quote; само наличие ключей не доказывает цену.

Для Hailuo 3.0 принят точный initializer текущей формы. Предыдущий одно-
изображённый кандидат `768p/4/frames` получил HTTP 422 и больше не допускается
генератором параметров. Новый `2K`/5 с/`16:9`/`omni-references` tuple один раз
вернул MCP-артефакт после HTTP 200 и GET-only reconciliation. Это не
подтверждение остальных вариантов или provider terminal status.

## Неопределённые ответы

После неизвестного upload/POST не повторяйте отправку автоматически. Получение
результата выполняет только чтение собственного чата и точного сообщения;
артефакт выдаётся после проверки owner echo, модели и завершённого видео.
Recovery хранится в памяти текущего процесса и не переживает перезапуск.
Проверка quote относительно баланса не является жёстким лимитом списания.

## Наблюдённые начальные результаты

Reader2367 вернул Fast и Live среди четырёх видео по одному текущему index GET,
шести history GET и шести detail GET. Для Fast запрошен tuple `768p/6s`;
получен H.264 768×768, 5.875 с, 50 516 байт. Для Live запрошен `720p/6s`;
получен H.264 720×720, 5.640 с, 167 109 байт. Связь с индексом, историей и
detail подтверждена (`CURRENT_LINK_INDEX_HISTORY_DETAIL_BOUND`, gaps 0).
Восстановление не выполняло upload или generation. Измеренные размеры и
длительность относятся к этим двум объектам; они не доказывают одинаковое
соотношение сторон, ровно шесть секунд, provider terminal status или другие
сочетания настроек.

Старый `hailuo-3.0` tuple ранее вернул HTTP 422. Новый
`2K/5s/16:9/omni-references` tuple дал один результат: H.264 2048×1170,
5.166667 с; AAC и контейнер — 5.175 с, 511 064 байта. Связанный artifact
получен после одного generation HTTP 200 и GET-only reconciliation, с gaps 0.
Разрешение 2048×1170 не имеет точного соотношения сторон 16:9, несмотря на
запрос; остальные Hailuo 3.0 параметры не подтверждены.
