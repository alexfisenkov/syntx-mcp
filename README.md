# SYNTX MCP — alpha

Публичный исходный проект MCP-сервера для каталога SYNTX AI, per-user account
linking и некоторых явно описанных image, video и audio flows. Это ранняя
разработка, а не полный клиент SYNTX и не обещание совместимости со всеми
моделями, настройками или MCP-хостами.

## Покрытие и ограничения

### Seedance 2.5 Editor: контракт настроек и запроса

Команда `syntx_get_seedance_editor_source` доступна без входа и сети. Она
возвращает закреплённый source-профиль редактора: отдельные `seedance-editor`
и scope `tool_video_inpaint`, upstream `seedance-2.5`, `mode=edit`,
`ai_name=seedance`, варианты разрешения `480p`/`720p`/`1080p`.
Внутренний ключ `seedance-2.5-editor` не является строкой публичного каталога.

Добавлены строгая проверка параметров и внутренняя сборка запроса с одним
исходным видео, пока без кадров-референсов. Это ещё не работающая генерация
Editor: цена/доступ, проверенная загрузка, отправка и получение результата
требуют дальнейшей интеграции. Профиль явно сохраняет
`dispatch_allowed=false`, `runtime_usable=false` и
`backend_acceptance=UNPROVEN`; неизвестные ограничения не заимствуются из T2V.
Новые source/wire/SDK-сценарии и два затронутых runtime/stdio-сценария прошли
локально; финальная Linux/Node 24 CI также проверила сборку и public security.
Это не live-приёмка модели и не проверка всех ОС или MCP-хостов.

Для последующей интеграции подготовлены отдельный чат редактора, проверка
MP4/MOV по метаданным (4–30 секунд), cost-параметры и проверка свежих снимков
цены/баланса. Эти внутренние блоки ещё не соединены в MCP-генерацию Editor.

### WAN 2.7 Video Edit: отдельная owner-группа

Отдельная owner-stdio группа для точной модели `wan_27_videoedit` (`wan_video`).
Она не включает WAN R2V или WAN 3.0 Edit. Профиль и локальные проверки
привязаны к исследованной форме, но не доказывают приёмку запроса провайдером,
его defaults или фактический размер списания.

#### Включение

Группа выключена по умолчанию. Чтобы получить локальный конфиг с этой группой,
запустите helper:

```sh
syntx-mcp-media-config --confirm-enable-paid-tools --include-wan27-videoedit
```

Флаг `--confirm-enable-paid-tools` обязателен. При совместном выборе с Kling 4
добавляйте `--include-kling4` только после этого подтверждающего флага.
Helper печатает конфигурацию; сам запуск не загружает файлы и не отправляет
генерацию.

Конфигурация owner stdio использует независимую группу и путь к доверенному
локальному `ffprobe`:

```json
{
  "SYNTX_OWNER_WAN27_VIDEOEDIT": "1",
  "SYNTX_OWNER_WAN27_VIDEOEDIT_FFPROBE_PATH": "<absolute path to trusted ffprobe executable>",
  "SYNTX_OWNER_WAN27_VIDEOEDIT_MAX_VIDEO_FILE_BYTES": "67108864"
}
```

Предел видео по умолчанию — 67 108 864 байта (64 MiB); оператор может задать
целое число от 1 до 104 857 600 байт (100 MiB). Это локальный предел одного
видео, а не обещание лимита MCP-хоста. Лимит изображения — 20 MiB. Для включения
нужен абсолютный путь к самому доверенному файлу `ffprobe`, не symlink;
бинарный файл группа не устанавливает. Публичный HTTPS, установленный клиент и матрица MCP-хостов этим
не подтверждаются.

#### Инструменты

Группа регистрирует шесть команд:

- `syntx_owner_get_wan27_videoedit_source` — показать закреплённый профиль и
  локальные ограничения; без загрузки и генерации.
- `syntx_owner_upload_wan27_videoedit_reference` — проверить и загрузить один
  собственный файл, вернуть временный `reference_handle`, не URL.
- `syntx_owner_generate_wan27_videoedit_video` — один явный запрос по своим
  handles.
- `syntx_owner_reconcile_wan27_videoedit_video` — GET-only сверка уже
  отправленного запроса.
- `syntx_owner_list_wan27_videoedit_recoveries` — список recovery текущего
  процесса.
- `syntx_owner_get_wan27_videoedit_result_page` — страница уже наблюдавшихся
  результатов.

Используйте обычный per-user вход SYNTX и его текущий `link_attempt_id`.
Сначала прочитайте source-инструмент, затем загрузите ровно одно собственное
видео и, при необходимости, до четырёх собственных изображений. Передайте
полученные `reference_handles` в нужном порядке. Входные URL, роли, нативные
настройки, source-duration и поля цены не принимаются от вызывающей стороны.

#### Параметры генерации

Укажите явно точную `model_id`, непустой `prompt`, `resolution`, `aspect_ratio`,
`audio_setting`, `prompt_extend`, `seed`, `duration_mode` и упорядоченные
`reference_handles`. Например:

```json
{
  "link_attempt_id": "<current own link attempt>",
  "model_id": "wan_27_videoedit",
  "prompt": "Смени освещение на мягкий утренний свет, сохрани движение камеры.",
  "resolution": "720P",
  "aspect_ratio": "16:9",
  "audio_setting": "origin",
  "prompt_extend": false,
  "seed": 0,
  "duration_mode": "preserve_input",
  "reference_handles": ["<video reference_handle>"]
}
```

Допустимы `resolution`: `720P` или `1080P`; `aspect_ratio`: `16:9`, `9:16`,
`1:1`, `4:3` или `3:4`; `audio_setting`: `auto` или `origin`. Это настройка
аудио результата, не разрешение загружать аудиофайл. `prompt_extend` — boolean.
`seed` — `null` либо целое число от 0 до 2 147 483 647; ноль сохраняется как
валидное значение. Локальный предел prompt — 1500 UTF-16 code units; эта единица
измерения не подтверждена отдельно исходником сайта.

Исходное видео должно быть заранее обрезано до 2–10 секунд: MCP не выполняет
crop. Длительность берётся из свежей локальной проверки ffprobe как максимум
конца аудио- или видеодорожки в секундах; длинная аудиодорожка тоже может
влиять на измеренную длительность. В режиме `preserve_input` поле `video_duration` сохраняет
измеренную дробную длительность с округлением до сотых. В режиме `custom`
передайте `custom_video_duration`: целое число от 2 до меньшего из 10 и
`floor(длительности исходника)`. В `preserve_input` это поле запрещено.

#### Файлы и безопасность повторов

Видео: MP4 или QuickTime/MOV. Изображения: JPG/JPEG, PNG, BMP и WebP. Ширина и
высота каждого файла должны быть в пределах 240–4096 пикселей. Для BMP
принимается только локально поддерживаемая структура. Максимум — одно видео и
четыре изображения; нужен ровно один уже обрезанный исходник-видео. Проверка
изображений анализирует структуру, видео — метаданные ffprobe; полного
декодирования пикселей нет.

Перед созданием чата и снова перед единственным запросом генерации проверяются
текущий план, доступ к модели, конечная котировка и баланс. Это предварительная
проверка, не жёсткий лимит списания: фактическая цена провайдера может отличаться.
Группа не покупает и не продлевает подписку.

Handles и recovery действуют только в памяти текущего процесса; handles
истекают через 15 минут. Не повторяйте upload или генерацию при неопределённом
исходе. Сохраните `recovery_id` и используйте только reconcile. После отправки
запроса с известным ACK чтение результата не требует повторной загрузки после
истечения handles. Если ACK не
получен, результат может остаться неизвестным; локальная система не достраивает
недостающую привязку. Статус `completed` означает локально наблюдавшийся и
привязанный артефакт, а не подтверждённый terminal-статус провайдера.

#### Статус подтверждения

Профиль, локальная валидация и цепочка генерации проверены на синтетических
данных. Дополнительно настоящий MCP SDK и собранный runtime прошли сценарий
«одна загрузка → две проверки подписки/цены/баланса → один GEN → GET результата
после 16 минут», без повторного GEN. Проверены opt-in/default-off и запрет
совместного durable-режима до входа. Это локальные тесты с синтетическим HTTP,
не установленный stdio и не живая генерация.

17 октября подтверждён отдельный реальный SDK/owner-runtime MCP-кейс с
InMemory transport: одна загрузка своего двухсекундного MP4, один чат и один
generation POST; настройки `720P`, `16:9`, audio `auto`, `prompt_extend=false`,
`seed=0`, `preserve_input`, без изображений. Только GET-recovery нашёл один
привязанный результат, MCP page — `completed`/`has_more=false`. Скачан H.264
MP4: 312655 байт, 1280×720, 2 секунды; метаданные и полное декодирование PASS.
Повторов upload/GEN не было, сеанс закрыт. Это один точный случай, не вся
матрица параметров или качество редактирования. Provider terminal, billing/
hard cap, durable recovery, установленный stdio, Windows/hosts и HTTPS
остаются неподтверждёнными.

### Kling 4 Keyframes и Omni: отдельная owner-группа

Добавлена отдельная группа для `kling_4_keyframes` и `kling_4_omni`. Она
выключена по умолчанию и не включается флагами старого Kling. Для конфигурации
с этой группой используйте:

```sh
syntx-mcp-media-config --confirm-enable-paid-tools --include-kling4
```

Либо задайте в owner stdio `SYNTX_OWNER_KLING4=1` и
`SYNTX_OWNER_KLING4_FFPROBE_PATH` — абсолютный путь к доверенному `ffprobe`.
`SYNTX_OWNER_KLING4_MAX_VIDEO_FILE_BYTES` по умолчанию равен `67108864`
(64 MiB); оператор может выбрать целое число байтов от 1 до `314572800`
(300 MiB). Это локальный ресурсный лимит видео, не обещание размера,
доступного в каждом MCP-хосте. Обычный HTTP и durable-профиль группу не включают.

Шесть команд:

- `syntx_owner_get_kling4_source` — параметры и отдельные локальные лимиты
  выбранной `model_id`, без сети;
- `syntx_owner_upload_kling4_reference` — загрузка собственных байтов в
  текущий связанный аккаунт, возврат временного handle без приватного URL;
- `syntx_owner_generate_kling4_video` — один запрос с явными настройками;
- `syntx_owner_reconcile_kling4_video` — только GET существующего recovery;
- `syntx_owner_list_kling4_recoveries` — список recovery текущего процесса;
- `syntx_owner_get_kling4_result_page` — страница уже наблюдавшихся результатов.

Генерация требует `link_attempt_id`, точную `model_id`, `version="4.0"`,
`mode="standart"` (720p) либо `"hd"` (1080p), `aspect_ratio` из
`16:9`, `1:1`, `9:16`, `21:9`, целый `video_duration` от 3 до 30 секунд,
`native_audio`, `prompt` и упорядоченный `reference_handles`. Скрытых defaults
нет. У Keyframes `native_audio` обязательно `true`; у Omni — явное boolean.
Промпт ограничен локально 24 000 UTF-16 units; `[[ref:N]]` ссылается на
1-based порядок handles. Сырые URL, роли, timestamps, стоимость и старые
`temperature`/`camera_movement`/`multi_shots` не являются входами инструмента.

Keyframes принимает только изображения, не более
`min(video_duration + 1, 10)`. Omni — до 10 изображений и 5 видео, при сумме
длительностей выбранных видеореференсов до 30 секунд. Пустой список допускается
локальным контрактом с непустым промптом, но приёмка такого варианта провайдером
не проверена. Одинаковое содержимое дважды в одном запросе локально отклоняется.

Изображения: JPEG/JPG, PNG и консервативное подмножество AVIF, до 30 MiB,
стороны 300–10 000, отношение ширины к высоте 0.4–2.5. Видео Omni: MP4/MOV,
стороны 700–10 000 и длительность отдельного файла 3–30 секунд, с указанным
операторским лимитом. Ограничения основаны на C19 и локальных guards; они не
доказывают приёмку формата/кодека. Изображения структурно проверяются, видео
проходит `ffprobe`, полного декодирования пикселей нет. Известные PQ/HLG HDR
метаданные отклоняются; отсутствие HDR-метаданных не доказывает SDR.

Необязательное имя файла в ответе загрузки — только метаданные: корректное
переименованное имя не меняет принадлежность reference. Оно не передаётся
в генерацию. Некорректные имена отклоняются; проверки URL, MIME, размера,
статуса, ID и привязки к текущему клиенту/аккаунту сохраняются.

Перед чатом и повторно перед GEN проверяются текущие активный платный план,
доступ к точной модели, конечная цена и баланс. Для Omni цена учитывает
длительность именно выбранных входных видео отдельно от длительности
результата. Это preflight, не жёсткий лимит списания. Handles действуют до
15 минут и привязаны к owner/attempt/model/client; recovery — process-local.
При неизвестном исходе POST запрещён автоматический повтор. Потерянный ACK
может остаться `OUTCOME_UNKNOWN`; GET не выдумывает недостающую привязку.

Проверено локально: настоящие сервисы и MCP SDK, загрузка → два preflight →
GEN → история → результат для обеих моделей с синтетическим HTTP. Это не
живые генерации SYNTX. Реальные K4-видео, все сочетания настроек, Windows и
матрица MCP-хостов пока не подтверждены. `completed` означает только
`LOCAL_OBSERVED_AVAILABILITY_ONLY`, не terminal/billing/provider-acceptance.

Отдельный живой пилот подтвердил обычный Telegram-вход и текущие проверки
аккаунта/доступа/цены. Первая загрузка вернула `UPLOAD_OUTCOME_UNKNOWN`;
вторая загрузка, чат и GEN не отправлялись. Причина не установлена, видео
не получено, запрос не повторялся. Изменение обработки имени файла само
по себе не доказывает причину или исправление этого наблюдения.

### Veo Omni: owner T2V без references

`syntx_get_veo_omni_parameters` при `SYNTX_OWNER_VEO_T2V=1` остаётся read-only отчётом общих параметров:
он перечисляет типы входа `text`, `image`, `references`, качества и длительности,
но не разрешает dispatch. Описанная здесь T2V-группа охватывает только
текстовый вариант `veo_omni`; отдельная группа для файлов описана ниже.

Owner-stdio группа выключена по умолчанию. Для явного включения задайте
`SYNTX_OWNER_VEO_OMNI_T2V=1`. Обычный запуск сервера не включает её автоматически;
обычный HTTP-сервер эти инструменты не регистрирует. Группа предоставляет четыре
команды:

- `syntx_owner_get_veo_omni_t2v_source` — read-only source-профиль текстового
  варианта;
- `syntx_owner_generate_veo_omni_t2v` — одна явная T2V-генерация;
- `syntx_owner_reconcile_veo_omni_t2v` — GET-only восстановление того же запроса;
- `syntx_owner_list_veo_omni_t2v_recoveries` — список process-local recovery
  ссылок текущего owner-процесса.

Для генерации укажите текущий `link_attempt_id`, непустой prompt длиной 8–50 000
Unicode-символов по кодовым точкам, числовой `upscale` (`0` — 720p, `1` — 1080p, `2` — 4K, `3` — 360p
Draft), `aspect_ratio` (`16:9` или `9:16`) и `video_duration` (4, 6, 8 или 10
секунд). Значения нужно передать явно: effective defaults неизвестны. Сервер
фиксирует текстовый `type` и пустой `file_urls`; модель и режим задаёт профиль.
Входы с файлами, references, caller-supplied model/wire IDs и другие режимы не
принимаются. Какие сочетания качества и длительности принимает сервис, ещё не
подтверждено; неподтверждённые ограничения в профиль не добавлялись.

Перед созданием чата и ещё раз перед отправкой runtime проверяет текущую платную
подписку, доступ к модели, свежую конечную цену и баланс. Если цены нет, баланс
недоступен или он ниже выбранной цены, запрос блокируется. Это сравнение с
текущим балансом, а не жёсткий лимит списания: фиксированный spend cap не задан,
а стоимость и состояние аккаунта могут измениться.

Запрос с неопределённым результатом не повторяйте. Используйте тот же
`recovery_id` только через GET-only reconciliation. Recovery-состояние
process-local и теряется при закрытии или перезапуске процесса. Ответ с
`reviewed` означает, что локально получен и привязан видео-артефакт; это не
подтверждает финальный статус задания провайдера, точную стоимость или возврат.

Локальные проверки профиля, runtime и MCP SDK не являются живой генерацией.
Приёмка T2V-запроса провайдером и результат реальной Veo Omni генерации этим
изменением не подтверждены. Полная матрица настроек Omni остаётся непроверенной.

### Veo Omni: изображения и видеореференсы в отдельной owner-группе

Эта группа для `veo_omni` / `veo3` работает отдельно от уже описанного
текстового T2V. Флаг references не включает T2V, а T2V не открывает работу с
файлами. Группа регистрируется только в локальном owner stdio; обычный HTTP
сервер её не включает.

Для owner stdio задайте отдельные операторские переменные:

```json
{
  "SYNTX_OWNER_VEO_OMNI_REFERENCES": "1",
  "SYNTX_OWNER_VEO_OMNI_REFERENCES_FFPROBE_PATH": "/absolute/path/to/ffprobe",
  "SYNTX_OWNER_VEO_OMNI_REFERENCES_MAX_FILE_BYTES": "67108864"
}
```

Путь к доверенному `ffprobe` обязателен даже если планируются только
изображения; сам бинарный файл не устанавливается. Проверка видео запускается
при загрузке и читает metadata, не декодируя видео. Максимум по умолчанию —
64 MiB на файл. Оператор может задать целое число байт от 1 до 1 048 576 000;
большие значения требуют соответствующего объёма памяти при декодировании
base64 и формировании upload. Параметром инструмента этот предел менять нельзя.

| Инструмент | Назначение |
| --- | --- |
| `syntx_owner_get_veo_omni_reference_source` | Показать закреплённые controls и отдельно локальные ограничения |
| `syntx_owner_upload_veo_omni_reference` | Проверить и загрузить один собственный файл, вернуть opaque handle |
| `syntx_owner_generate_veo_omni_references` | Отправить одну явную генерацию по своим handles |
| `syntx_owner_reconcile_veo_omni_references` | GET-only чтение прежней операции без повторной генерации |
| `syntx_owner_list_veo_omni_reference_recoveries` | Показать собственные process-local recovery записи |
| `syntx_owner_get_veo_omni_reference_result_page` | Читать уже обнаруженные результаты постранично |

Обычный порядок работы: завершите per-user вход SYNTX, прочитайте source tool,
загрузите собственные файлы по одному, затем передайте полученные
`reference_handles` в нужном порядке в generation tool. Введите `prompt`,
`input_type`, `upscale`, `aspect_ratio` и `video_duration` явно. Чужие URL,
model/chat IDs, file roles, wire поля и cost-only режим в запрос генерации не
принимаются.

| Поле | Допустимые значения |
| --- | --- |
| `input_type=image` | 1–2 изображения, без видео |
| `input_type=references` | 1–7 изображений без видео либо одно видео с 0–5 изображениями |
| `upscale` | `0` — 720p, `1` — 1080p, `2` — 4K, `3` — 360p Draft |
| `aspect_ratio` | `16:9`, `9:16` |
| `video_duration` | `4`, `6`, `8`, `10` секунд |
| `prompt` | 8–50 000 code points; TAB, LF и CR допустимы, остальные запрещённые управляющие символы отклоняются |

В prompt можно поставить локальный placeholder `[[ref:N]]`: `N` — номер handle
в исходном порядке, начиная с 1. Это соглашение MCP, а не синтаксис сайта.
Сервер заменяет только такие placeholders, не добавляя к остальному prompt
префикс или пробелы. Длина проверяется повторно после подстановки; разрешённые
переносы строк и табуляции сохраняются.

Публичные metadata перечисляют JPEG/JPG, PNG, WebP, AVIF, MP4 и QuickTime,
задают максимум 1 048 576 000 байт на файл и максимальную длительность видео
10.2 секунды. Локальная политика по умолчанию остаётся 64 MiB. Валидатор
консервативно принимает статические JPEG/PNG/WebP/AVIF-изображения (JPG
нормализуется как JPEG); анимированный WebP, motion/derived AVIF и часть
сложных AVIF properties отклоняются. Локальная проверка осматривает структуру
и metadata; полного декодирования изображения или видео нет. MIME и расширение
сами по себе не гарантируют приём.

Перед созданием чата и снова перед генерацией проверяются активный платный
план, доступ к точной модели, конечная цена и достаточный баланс. Для
image-only references в запрос цены идут `upscale` и `video_duration`; для
video reference добавляется `mode=video_ref` только в запрос цены. Это
сравнение с текущим балансом, а не жёсткий лимит списания.

Файловые handles временные — до 15 минут — и привязаны к текущему owner,
attempt, клиенту и процессу. После перезапуска они не восстанавливаются.
`UPLOAD_OUTCOME_UNKNOWN` не разрешает автоматически повторять загрузку. Если
исход generation POST неизвестен, не запускайте generation снова: сохраните
`recovery_id` и используйте только reconcile. Recovery и результаты требуют
текущей авторизованной сессии и точной связи с owner ACK/message/object IDs.
Локальная доступность видео не подтверждает provider terminal status,
полную стоимость, output count или возврат оплаты.

Статический профиль закреплён за C19 и frontend build `1792156098`. Его
`runtime_usable=false` и `dispatch_allowed=false` описывают source-only отчёт;
реальный запуск отдельно проходит runtime-проверки и два платёжных preflight.
Эти значения и локальные тесты не являются доказательством совместимости с
текущим UI или приёмки запроса провайдером.

Сквозной локальный MCP SDK/InMemory тест прошёл через фактические сервисы:
загрузка → opaque handle → одна генерация → результат → список и страница.
HTTP-ответы были синтетическими; реального нового видео, installed/OS/HTTPS
приёмки или подтверждения биллинга этот тест не доказывает.

В отдельном owner-пилоте 2026-10-17 через официальный MCP SDK/InMemory и обычный
Telegram-вход подтверждены активный платный план, доступ к модели, конечная цена и баланс.
Для одного собственного PNG выполнены одна загрузка, одна генерация и две
GET-only сверки; наблюдался один MP4: H.264 640×360, 4,01 с, 96 кадров,
212 586 байт с AAC. HTTPS-загрузка без редиректа и строгий полный FFmpeg decode
прошли; после упорядоченного закрытия манифест потреблён, процесс и сокет отсутствовали.
Подтверждена только комбинация image, upscale=3 (360p Draft), 16:9, 4 с.
Другие режимы/настройки, T2V, статус провайдера, списание/output count, ОС клиентов и HTTP не проверены; полной MCP-приёмки нет.

В одном процессе одинаковое намерение владельца (промпт, настройки и содержимое
файлов) может быть отправлено только один раз. Новые handles или повторный вход
не снимают эту защиту. Не изменяйте запрос ради обхода неопределённого исхода.

### Flux3 I2V и V2V: отдельная owner-stdio группа

В исходниках есть шесть инструментов для двух отдельных video-моделей:
`flux3_i2v` и `flux3_v2v`. Группа выключена по умолчанию и не добавляется в
обычный HTTP runtime. Для включения только в локальном owner stdio задайте
операторские переменные:

```text
SYNTX_OWNER_FLUX3_VIDEOS=1
SYNTX_OWNER_FLUX3_FFPROBE_PATH=/absolute/path/to/trusted/ffprobe
SYNTX_OWNER_FLUX3_UPLOAD_DESTINATION=hidden
```

`SYNTX_OWNER_FLUX3_UPLOAD_DESTINATION` принимает `hidden` или `uploaded`.
Путь к `ffprobe` должен быть абсолютным и доверенным. `ffprobe` запускается
только при явном вызове upload; старт сервера не проверяет файл и не генерирует
видео. Шаблон конфигурации можно вывести существующей командой только после
явного подтверждения платных tools:

```sh
node scripts/print-media-mcp-config.mjs --confirm-enable-paid-tools
```

Инструменты:

- `syntx_get_flux3_video_parameters` — принимает явный `model_id` (`flux3_i2v`
  или `flux3_v2v`) и возвращает профиль выбранной модели;
- `syntx_owner_upload_flux3_video_reference` — загружает один собственный
  reference-файл и возвращает непрозрачный `flux3_reference_handle`;
- `syntx_owner_generate_flux3_video` — создаёт один запрос с этим handle;
- `syntx_owner_reconcile_flux3_video` — GET-only сверка одного recovery;
- `syntx_owner_list_flux3_video_recoveries` — ограниченный список своих
  process-local recovery-записей;
- `syntx_owner_get_flux3_video_result_page` — читает страницу уже наблюдавшихся
  результатов.

Сначала используйте обычный per-user Telegram link flow и передавайте один и
тот же `link_attempt_id` в upload и generate. Для I2V можно загрузить от 1 до
10 изображений JPEG/PNG/WebP, каждое до 10 MiB. Для V2V принимается один MP4 до
50 MiB. Это локальные границы этой реализации; WebM, QuickTime и ссылки на
произвольные URL через инструменты не принимаются. Upload не принимает URL,
измеренные dimensions/duration или путь к файлу от вызывающего кода.
Для I2V локальная проверка структуры и размеров не декодирует все пиксели; для
V2V `ffprobe` читает метаданные, но это не полное декодирование, проверка
качества или подтверждение приёмки провайдером.

Generate требует явные `model_id`, `prompt`, `flux3_reference_handles` и все
три `parameters`: `resolution` (`hd`/`fhd`), `video_duration` (I2V 5–20 секунд;
V2V 5–15 секунд) и `generate_audio` (`true`/`false`). Aspect ratio фиксирован
как `auto`; `n`, draft, URL, размеры и измеренная длительность источника не
принимаются. Эффективные defaults и допустимость сочетаний контролов не
подтверждены, поэтому передавайте значения явно.

Перед dispatch код заново проверяет linked account, доступ к модели и текущую
оценку цены; сведения о подписке читает отдельно, без выдуманного требования
активного тарифа при `access: true` для этой модели. По source-bound cost contract в запрос оценки входят
`resolution` и `video_duration`; draft остаётся unset. Это не жёсткий лимит и
не гарантия фактического списания. При `OUTCOME_UNKNOWN` не повторяйте generate:
используйте recovery того же запроса и только GET-сверку. Неопределённый upload
(`UPLOAD_OUTCOME_UNKNOWN`) также нельзя повторять; generation recovery он не
создаёт. Список
восстановлений хранится в памяти процесса и не переживает перезапуск. Страница
результата может содержать URL выходного артефакта; provider acceptance,
provider terminal status и полное число результатов не подтверждаются этим
локальным кодом.

Проверены два ограниченных локальных MCP-кейса, по одному на режим; оба
использовали `hd`, `video_duration: 5` и `generate_audio: false`. I2V: загружены
два собственных PNG, выполнена одна генерация и две GET-only сверки того же
recovery; страница MCP вернула одно наблюдаемое видео. MP4 скачан по HTTPS и
полностью декодирован FFmpeg: H.264, 1280×704, 5,041667 секунды, 121 кадр,
1 921 569 байт. V2V: загружен один собственный MP4 длительностью 6 секунд,
выполнена одна генерация и одна GET-only сверка; страница MCP вернула одно
наблюдаемое видео. MP4 также скачан по HTTPS и полностью декодирован FFmpeg:
H.264, 1280×704, 5 секунд, 120 кадров, 1 921 271 байт.

Это два отдельных результата наблюдаемой доступности, не полная матрица
сочетаний и не известное общее число результатов. Provider terminal status,
окончательное списание и жёсткий лимит стоимости не подтверждены. HTTPS-сервер
MCP, Windows, остальные клиенты, durable restart и другие параметры не проверены.

### Grok V2V: собственный видеооригинал в owner-stdio

`grok_v2v` подключён отдельной группой owner-stdio, выключенной по умолчанию;
она не включается в обычный или HTTP runtime. Для локального запуска задайте
операторскую конфигурацию:

```text
SYNTX_OWNER_GROK_V2V=1
SYNTX_OWNER_GROK_V2V_FFPROBE_PATH=/absolute/path/to/trusted/ffprobe
SYNTX_OWNER_GROK_V2V_UPLOAD_DESTINATION=hidden
```

Путь должен быть абсолютным и доверенным; destination — `hidden` или `uploaded`.
Шаблон конфигурации можно вывести только с явным подтверждением:

```sh
node scripts/print-media-mcp-config.mjs --confirm-enable-paid-tools
```

Старт сервера не вызывает `ffprobe`, не загружает файл и не запускает генерацию.
Группа содержит шесть инструментов с закрытыми схемами: поля ниже обязательны,
кроме явно помеченных `?`; дополнительные поля отклоняются.

| Инструмент | Входные поля |
| --- | --- |
| `syntx_get_grok_v2v_parameters` | `model_id: "grok_v2v"` |
| `syntx_owner_upload_grok_v2v_reference` | `link_attempt_id`, `model_id: "grok_v2v"`, `filename`, `mime_type`, `content_base64` |
| `syntx_owner_generate_grok_v2v` | `link_attempt_id`, `model_id: "grok_v2v"`, `prompt`, `grok_reference_handle` |
| `syntx_owner_reconcile_grok_v2v` | `link_attempt_id`, `recovery_id` |
| `syntx_owner_list_grok_v2v_recoveries` | `link_attempt_id`, `limit?` |
| `syntx_owner_get_grok_v2v_result_page` | `link_attempt_id`, `recovery_id`, `offset?` |

Upload возвращает непрозрачный `grok_reference_handle`, не URL. Getter принимает
явный model ID и возвращает только source-reviewed профиль: `effective_defaults`,
`runtime_usable` и `dispatch_allowed` остаются `UNKNOWN`, `false` и `false`.
Этот статический отчёт сам по себе не является разрешением на генерацию.

Принимается один файл размером до 50 MiB, с согласованными MIME и расширением:
MP4 (`video/mp4`, `.mp4`) или QuickTime (`video/quicktime`, `.mov`). Локальный
параметр `filename` ограничен 128 ASCII-символами по локальной схеме; это не
заявление об ограничении провайдера. `ffprobe` запускается только по явному
вызову upload и требует доверенный абсолютный путь к обычному файлу, не symlink.
Из его metadata выводятся длительность и разрешение; длительность должна быть
в диапазоне 1–8,7 секунды до округления до двух знаков. Разрешение выбирается
локально по площади:
409 920 пикселей и выше — `720p`, ниже — `480p`; `aspect_ratio` зафиксирован в
`null`. Эти значения нельзя передать или переопределить через generate.
Wire-проекция содержит измеренные `video_duration` и `resolution`; количество
выходов неизвестно. Prompt должен содержать непустой после `trim` корректный
Unicode-текст длиной не более 2 000 UTF-16 code units; это локальная схема.
Локальное чтение metadata не является полным декодированием видео или
доказательством приёмки провайдером.

Перед генерацией выполняются два свежих чтения аккаунта и model access; требуется
`access: true` и конечная оценка не выше доступного баланса. Это проверка перед
dispatch, а не жёсткий лимит списания или гарантия цены. Значения подписки
читаются отдельно и не заменяют model access.

Upload и generate привязаны к одному owner/attempt/client. Не повторяйте upload
после `UPLOAD_OUTCOME_UNKNOWN`: такой upload не создаёт generation recovery.
Не повторяйте generate после `OUTCOME_UNKNOWN`; используйте его `recovery_id` и
GET-only reconcile. Handles действуют до 15 минут; recovery хранится в памяти
процесса и теряется после перезапуска. Результат
означает только локально наблюдённую доступность проверенных видеоартефактов;
provider terminal status, общее число выходов и enforceable cost cap остаются
неподтверждёнными.

На source commit `2da173f6c2b48e9addc7a565c9937dd9533290ff` прошёл один
owner-linked Grok V2V пилот: один собственный 5-секундный MP4,
одна загрузка и одна генерация с известным ACK. После начального
`OUTCOME_UNKNOWN` результат был восстановлен двумя GET-only reconcile-запросами;
итого зафиксированы три history GET, один result GET, одна страница MCP и одно
наблюдённое видео. Результат скачан по HTTPS и полностью декодирован локальным
FFmpeg через `file` protocol: 1 470 471 байт, H.264, 1280×704, 4,708333 секунды,
113 кадров. Независимая проверка подтвердила закрытие процесса, отсутствие
socket-parent и startup manifest, потребление manifest и приватный режим файла
`0600`.

Это подтверждает только один пилотный tuple, а не остальные параметры или
форматы. MOV/QuickTime, Windows, удалённый HTTPS MCP endpoint и совместимость
клиентского host, provider terminal status, общее число выходов, списание,
жёсткий cost cap и durable recovery после перезапуска не подтверждены.
Количество выходов остаётся неизвестным; статический профиль и его
`runtime_usable: false` / `dispatch_allowed: false` — отдельный source-report,
не результат этого пилота.

WAN 2.6 R2V и R2V Flash подключены к восьми default-off owner-stdio командам:
проверка и загрузка references, генерация, GET-only восстановление и результаты.
Один реальный Flash-запуск остался `OUTCOME_UNKNOWN` без подтверждённого ACK и
артефакта; регулярный вариант live не проверен. Причина и списание неизвестны,
повторять неопределённый запрос нельзя. Подробные ограничения — в разделе R2V

### WAN 3.0 Text-to-Video

Отдельный профиль `wan_30_t2v` использует текущую форму и наблюдавшийся запрос
сайта, не параметры WAN 2.7. Он доступен через существующую группу

Для `syntx_owner_generate_wan_t2v_video` передайте текущий `link_attempt_id`,

{
  "aspect_ratio": "16:9",
  "resolution": "480P",
  "video_duration": 2,
  "prompt_extend": true,
  "seed": null,
  "native_audio": false,

В одном обычном веб-кейсе Basic/480P/2s получен, скачан и полностью декодирован

установленного stdio-пакета, HTTPS, всех MCP-хостов или полной матрицы настроек.

WAN 3.0 Video Edit доступен отдельной default-off owner-stdio группой ниже.

`recovery_id` для GET-only reconcile и чтения результатов.
Защита от повтора и recovery пока process-local, не переживают перезапуск.

В диагностике результата может быть необязательное поле
`diagnostic.http_status_observed: "HTTP_422_OBSERVED"`. Оно означает только,
что HTTP 422 был замечен у POST генерации Topaz Astra; тело ответа
отбрасывается, а статус генерации остаётся `OUTCOME_UNKNOWN`. В старой форме
диагностики этого поля нет, поэтому его отсутствие не доказывает, что HTTP 422
не происходил. Маркер сохраняется в GET-only reconcile и списке recovery; он
не раскрывает причину ответа, terminal status или списание и не разрешает
повторять generate.

Список обрабатывает только узнаваемые Topaz-чаты, созданные MCP; totals
относятся ко всему upstream-списку, а результаты — к проверенному подмножеству.

отправлен ранее и остаётся UNKNOWN. Его исход не устанавливается отдельным
свежим чтением существующих результатов Topaz после обычного входа:
проверенного подходящего результата не найдено, артефакт не получен.
Скачиваний, загрузок, новых чатов и генераций в этом
чтении не было. Эти наблюдения не разрешают исход неопределённой генерации.
Фактические списания и все сочетания настроек не проверены.

### Topaz Enhance: отдельный owner-stdio профиль

`topaz_enhance` (`ai_name: topaz_ai`) — отдельный профиль, не Topaz Astra.
Шесть команд доступны только в owner-stdio группе, выключенной по умолчанию:

- `syntx_get_topaz_enhance_parameters` — статический профиль и ограничения;
- `syntx_owner_upload_topaz_enhance_original` — локальная проверка и загрузка MP4;
- `syntx_owner_generate_topaz_enhance` — один запрос по загруженному handle;
- `syntx_owner_reconcile_topaz_enhance` — GET-only восстановление;
- `syntx_owner_list_topaz_enhance_recoveries` — process-local список восстановлений;
- `syntx_owner_get_topaz_enhance_result_page` — чтение кэшированной страницы результата.

Для явного включения в stdio задаются `SYNTX_OWNER_TOPAZ_ENHANCE=1`,
`SYNTX_OWNER_TOPAZ_ENHANCE_FFPROBE_PATH` (абсолютный путь к доверенному
`ffprobe`) и `SYNTX_OWNER_TOPAZ_ENHANCE_UPLOAD_DESTINATION=uploaded` либо
`hidden`. Группа выключена, если флаг не задан или равен `0`; обычный HTTP
сервер её не включает. Команда печати owner-media-конфигурации включает такие
paid tools только при явном `--confirm-enable-paid-tools`; сама печать не
запускает инструменты или генерацию. Запуск MCP тоже не загружает файлы и не
начинает генерацию.

Upload принимает свой MP4 через `content_base64` и возвращает непрозрачный
`topaz_original_handle`, не URL. Generate использует тот же
`link_attempt_id`, `model_id: "topaz_enhance"`, handle и все 12 явных полей
`parameters`; prompt, `n`, URL файла и измеренные размеры/длительность от
вызывающего кода не передаются. Пример явного набора параметров:

```json
{
  "model_id": "topaz_enhance",
  "parameters": {
    "blur": 0,
    "halo": 0,
    "focus": "off",
    "grain": "off",
    "model": "rhea-1",
    "noise": 0,
    "details": 0,
    "preblur": 0,
    "upscale": 1,
    "prenoise": 0,
    "compression": 0,
    "interpolation": 60
  }
}
```

Это выбранные значения одного запроса, не defaults или доказанная матрица.
Допустимые модели: `ghq-5`, `rhea-1`, `prob-4`, `iris-3`, `gcg-5`; upscale:
`1`/`2`/`4`; interpolation: `24`/`25`/`30`/`45`/`50`/`60`. Числовые
диапазоны, `focus` и `grain` следует смотреть в
`syntx_get_topaz_enhance_parameters`; эффективные defaults и совместимость
комбинаций остаются неизвестны. `upscale: 4` локально отклоняется, если у
исходника ширина не меньше 1280 или высота не меньше 720. В wire фиксируются
`blend: 0` и `promode: 0`; это не дополнительные поля запроса.

Локальная реализация принимает только MP4
(до 50 MiB, от 2 до 26,25 секунды, максимум 10 000 кадров); публичная запись
модели также перечисляет WebM и QuickTime, но этот локальный путь их не
поддерживает. Доверенный `ffprobe` работает до 15 секунд и сообщает локальные
метаданные, а не полное декодирование, качество или приёмку провайдера.

16 октября 2026 года пройден один реальный локальный MCP-пилот: свой короткий
MP4, `rhea-1` / `upscale: 1` / `interpolation: 60` и остальные значения из
примера выше. Одна загрузка и одна генерация дали один результат после одного
GET-only reconcile; страница прочитана через MCP, файл скачан по HTTPS и
полностью декодирован FFmpeg (H.264, 854×480, 1,983333 секунды, 118 кадров).
Это проверка одного случая, не всех моделей Topaz или сочетаний параметров.
Перед каждым созданием чата и отправкой заново проверяются аккаунт,
подписка, доступ и конечная оценка по `resolution` и округлённому
`video_duration`; оценка должна быть ниже доступного баланса, но жёсткого
лимита или гарантии списания нет. При `OUTCOME_UNKNOWN` не повторяйте generate:
используйте тот же recovery для GET-only reconcile. Состояние и блокировка
повторов process-local и теряются при перезапуске. Приёмка провайдером и его
terminal status не подтверждены; установленный Windows stdio, HTTPS и другие
MCP-хосты не проверены.

### WAN: текущая политика звука и R2V через MCP

Для `wan_27_t2v` текущая форма скрывает `native_audio` и сбрасывает его в
`false`. MCP принимает только явное `native_audio: false`; `true` отклоняется,
а не исправляется молча. Отдельный `current_audio_policy` в отчёте параметров
указывает новый исходник; исторические source pins сохранены. Это политика
текущего веб-интерфейса, не утверждение о всех возможностях backend.

Для WAN 2.7 R2V добавлены внутренние блоки проверки исходных видео и
reference-изображений, выбора фрагмента и локальной обрезки. Они не означают
готовую R2V-генерацию через MCP. Изображения JPEG/JPG, PNG, BMP и WebP
проверяются по контейнеру и метаданным, без полного декодирования пикселей.
Ограничения исходного видео и изображения привязаны к архиву каталога и
местным ресурсным ограничениям, а не к подтверждённому приёму провайдером.

Внутренний нормализатор R2V проверяет шесть явных контролов: разрешение,
соотношение сторон, длительность видео, `prompt_extend`, `seed` и выключенный
`native_audio`. Он сверяет реальный манифест ссылок: `video_duration` ограничен
10 секундами при выбранном видео и 15 секундами без него. Для промпта закреплён
ресурсный предел 1500; это не измерение текущего UI. Эти параметры доступны
через MCP-команду чтения; реальная R2V-генерация у провайдера не проверена.

Нативная загрузка принимает только подлинную проверку изображения или
измеренный результат обрезки. Изображение отправляется в `uploaded`, выбранное
видео — в `hidden`; URL остаётся внутри контекста того же клиента.
Внутренний сервис связывает упорядоченный набор из 1–5 референсов с текущим
пользователем, проверяет точное число видео, срок действия и отзыв входа.
Неопределённая загрузка блокирует повтор по содержимому. Набор сам по себе
не даёт разрешения на генерацию.

Opt-in `SYNTX_OWNER_WAN27_R2V=1` добавляет девять owner-stdio команд:

- `syntx_get_wan27_r2v_parameters`;
- `syntx_owner_create_wan27_r2v_manifest`;
- `syntx_owner_upload_wan27_r2v_image`;
- `syntx_owner_upload_wan27_r2v_video`;
- `syntx_owner_finalize_wan27_r2v_manifest`.

После подготовки референсов доступны:

- `syntx_owner_generate_wan27_r2v`;
- `syntx_owner_reconcile_wan27_r2v`;
- `syntx_owner_list_wan27_r2v_recoveries`;
- `syntx_owner_get_wan27_r2v_result_page`.

Нужны абсолютные доверенные пути `SYNTX_OWNER_WAN27_R2V_FFPROBE_PATH` и
`SYNTX_OWNER_WAN27_R2V_FFMPEG_PATH`. Группа по умолчанию выключена; обычный
HTTP-сервер её не включает. Сначала создайте манифест с точным числом видео
`video_reference_count` (0–5), затем загрузите свои файлы как `content_base64`
с `filename`/`mime_type`. Видео дополнительно требует `start_seconds` и
`end_seconds`; число видео берётся из манифеста, не из запроса загрузки.
Все операции используют текущий `link_attempt_id` и `manifest_handle`.
Finalize возвращает безопасные метаданные без исходных URL/байтов/хешей.
Местные пределы — 20 MiB на изображение и 100 MiB на исходное видео; предел
MCP-хоста может быть меньше. Произвольные пути, URL и overrides метаданных
не принимаются. Манифест действует до 15 минут, process-local.

Внутренняя подготовка и нативная отправка R2V теперь реализованы: фиксированные
`shot_type: single`, `audio_setting: auto`, выключенный звук, типизированные
референсы и расчёт `duration` по выбранным сегментам. Одна отправка и GET-only
получение результата после истечения input TTL проверены на синтетическом HTTP.
Generate принимает тот же `link_attempt_id`, `model_id: "wan_27_r2v"`, готовый
`manifest_handle`, необязательный `prompt` и шесть явных полей верхнего уровня:
`resolution` (`720P`/`1080P`), `aspect_ratio`, целое `video_duration`,
`prompt_extend`, `seed` (null либо целое 0–2147483647), `native_audio: false`.
Вложенный объект `parameters` в MCP-вызове не используется. Длительность
ограничена 2–15 секундами без видео-референса и 2–10 секундами с ним;
доступные соотношения сторон возвращает команда параметров.

Перед созданием чата и ещё раз перед генерацией читаются свежие подписка,
доступ модели и конечная оценка цены. Стоимостные входы `resolution`,
`video_duration` и рассчитанный из выбранных референсов `duration` различаются.
Точный intent закрепляется до создания чата. Это не жёсткий лимит списания:
результат содержит `cost_cap_enforced: false`.

При `OUTCOME_UNKNOWN` не повторяйте generate или upload. Используйте
`recovery_id` из ошибки либо списка восстановлений для GET-only reconcile;
готовые ссылки находятся в `artifacts[].object_url`, следующие страницы —
через result-page. Подтверждённый ACK позволяет продолжить чтение после
истечения срока входного манифеста, но текущий вход пользователя всё ещё
должен действовать. Потерянный ACK может остаться неопределённым. Recovery,
референсы и защита от повтора process-local; перезапуск их теряет.

Полная цепочка MCP «загрузка → finalize → один GEN → видео» проверена через
официальный SDK на синтетических HTTP-ответах. В этой R2V-работе живой запуск
SYNTX не выполнялся; принятие провайдером, терминальный статус, качество и
фактические списания не подтверждены. Это не завершённое покрытие всех моделей.

`syntx-mcp-media-config --confirm-enable-paid-tools` включает эту группу в
выводимый конфиг с явными placeholders путей; замените их до запуска.
Команда только печатает конфигурацию и не запускает генерации.

Выбранный видеосегмент привязывается к измеренной частоте кадров; предел
составляет 5 секунд, делённых на число reference-видео. Локальная обрезка
кодирует CFR H.264 и сохраняет аудиодорожки. Целевые проверки выполнялись
на macOS и Linux; Windows-права временных файлов и полная переносимость ещё не доказаны.

### WAN 2.6 Image-to-Video

Исторический архив публичного каталога C396 содержит 41 AI-запись, 199 строк моделей
и 43 LLM-модели (165 активных и 34 неактивных строки моделей). Это каталог
обнаружения, а не список реализованных генераторов. Новый WAN 2.6 профиль
закреплён за C396; общий discovery default остаётся E551, чтобы изменения
каталога не переназначали старые source-bound профили. Отдельная opt-in группа
WAN 2.6 покрывает только `wan_26_i2v` и `wan_26_i2v_flash` и по умолчанию
выключена.

`SYNTX_OWNER_WAN26_I2V=1` включает семь owner-stdio инструментов:

- `syntx_owner_get_wan26_i2v_parameters`;
- `syntx_owner_upload_wan26_i2v_image`;
- `syntx_owner_upload_wan26_i2v_audio`;
- `syntx_owner_generate_wan26_i2v_video`;
- `syntx_owner_reconcile_wan26_i2v_video`;
- `syntx_owner_list_wan26_i2v_recoveries`;
- `syntx_owner_get_wan26_i2v_result_page`.

Вход включает ровно одно изображение и необязательный MP3 или PCM-WAV.
Для включения профиля нужен абсолютный путь к доверенному `ffprobe` в
`SYNTX_OWNER_WAN26_I2V_FFPROBE_PATH`, в том числе при работе только с изображением;
локальный probe измеряет аудиофайл до загрузки.
Параметры запрашиваются и передаются явно. `native_audio` поддерживается только
для Flash-модели. Перед платным запуском повторно проверяются текущий доступ к
аккаунту и свежая оценка стоимости; жёсткого лимита списания нет.

После `OUTCOME_UNKNOWN` не повторяйте платный POST. Используйте `recovery_id`
через GET-only reconcile, список восстановлений или чтение страницы результата.
Автоматические проверки WAN 2.6 синтетические и локальные. Отдельный MCP-пилот
выполнил одну генерацию; после неопределённого первого ожидания GET-only чтение
связало собственную историю и готовый видеообъект с непустой ссылкой. Повторного
запуска не было. Файл не скачивался и не декодировался: фактические параметры
видео, списание и terminal status провайдера этим не подтверждены.

Текущие account/access/quote проверки, запрет повторного POST и GET-only
восстановление включены; recovery остаётся в памяти процесса, жёсткого

Suno Cover имеет подтверждённые MP3-результаты для V6/V6_wild. В первой

чтения истории; последующее GET-only восстановление связало её с ACK владельца

как общие backend-ошибки без структурированного кода. Причина обеих ошибок,
статус завершения у провайдера и статус оплаты не установлены. Это не доказывает
глобальную недоступность Extend. Старые запросы не повторяются.

### Чтение загруженных файлов

Чтение загруженных файлов использует отдельный предел ответа 256 KiB:
он позволяет прочитать страницу до 100 записей с расширенными метаданными.
Остальные JSON-запросы сохраняют предел 64 KiB. Явно заданный оператором
`maxResponseBytes` по-прежнему ограничивает оба режима. Внешние URL и hash
из списка файлов не возвращаются в публичных результатах этого инструмента.
Этот предел не означает поддержку скачивания или восстановления image handle.

### Kling Image-to-Video

Opt-in `SYNTX_OWNER_KLING_I2V=1` добавляет пять инструментов:

- `syntx_owner_get_kling_i2v_parameters`;
- `syntx_owner_upload_kling_i2v_image`;
- `syntx_owner_generate_kling_i2v_video`;
- `syntx_owner_reconcile_kling_i2v_video`;
- `syntx_owner_list_kling_i2v_recoveries`.

Войдите обычным способом через Telegram, загрузите собственное изображение
и передайте полученный `image_handle` в генерацию. Загрузка принимает
`link_attempt_id`, `content_base64`, `filename` и `mime_type`.
JPEG/JPG, PNG, WebP и AVIF ограничены 30 MiB; обе стороны по метаданным
контейнера должны быть не меньше 300 пикселей. Это не полная проверка декодирования
изображения. Используется `destination=uploaded`, как в обычном видеовводе
сайта. SHA-256 возвращается как 64 hex-символа без префикса; исправлена
несогласованность между ответом сервиса и схемой MCP. URL файла и provider IDs
не возвращаются.

Генерация принимает `link_attempt_id`, `image_handle`,
`model_id: "kling_image2video"`, `prompt`, `version`, `mode`,
`video_duration`, `native_audio` и `temperature`.
Версии: 1.5, 1.6, 2.1-master, 2.5-turbo, 2.6, 3.0 и 3.0-turbo.
Температура задаётся явно во всех версиях: 0–1 с шагом 0.1, даже если сайт
скрывает этот контроль. Версия 3.0 дополнительно требует явное
`multi_shots: false` либо `true`. Для остальных версий поле не передаётся.
При `true` передайте готовый непустой `prompt`: он отправляется без изменений.
MCP не строит промпт из объектов сцен и не добавляет `settings.scenes` или
`multi_prompt`. В текущей форме сайта конструктор сцен также формирует общий
текст промпта, а не отдельный массив в запросе. Его текстовый форматтер в MCP
ещё не реализован.
Допустимые сочетания режимов, длительности и аудио проверяет схема инструмента;
версия 3.0-turbo позволяет не передавать промпт.

Новый `multi_shots: true` проверен через реальный runtime, MCP-сервер и
официальный SDK на синтетической цепочке «загрузка → один GEN → видео».
Это не новый живой результат SYNTX и не доказательство качества мультисцены
или фактической стоимости. Общие поля `camera_movement` и `motion` обнаружены
в текущей форме Kling и отражены в исходных метаданных, но не принимаются
этим I2V-интерфейсом; их применимость и отдельные контракты остаются открытыми.

Перед единственным POST читаются свежие тариф, доступ к модели и конечная
оценка стоимости. Оценка не является гарантией списания или верхним лимитом.
Результат содержит непрозрачный `recovery_id` и проверенные ссылки на видео.
При `OUTCOME_UNKNOWN` не повторяйте генерацию: используйте GET-only сверку
с теми же `link_attempt_id` и `recovery_id`.

Ссылки на изображения действуют 15 минут и привязаны к текущему аккаунту;
получение уже запущенного результата не требует продлевать ссылку изображения.
Восстановление после перезапуска процесса пока не реализовано.
Пять инструментов доступны только в явно включённом owner-stdio контуре;
обычный и HTTP-серверы их автоматически не включают.
Сквозная проверка через MCP подтвердила обычный вход, чтение доступа, загрузку
нового JPEG, генерацию и получение одного реального MP4: версия 2.6,
`mode=hd`, 5 секунд, `native_audio=false`, `temperature=0.5`. Видео H.264
1920×1080 скачано и полностью декодировано. Первое ожидание вернуло
`OUTCOME_UNKNOWN`; GET-only сверка получила результат без повторного POST.
Сессия закрыта. Это доказательство указанного сочетания, а не всех версий,
параметров или клиентов. Старые неопределённые загрузки не повторялись.

### Kling Keyframes: изображения, генерация и получение видео

Добавлена отдельная проверка настоящих JPEG/JPG, PNG и AVIF: до 50 MiB,
обе стороны не меньше 300 пикселей. WebP здесь не разрешён, в отличие от I2V.
Снимок байтов защищён от подмены и отзывается при освобождении; MIME и размеры
проверяются по контейнеру, не полным декодированием пикселей. Это локальная
проверка по закреплённому каталогу, не доказательство приёма провайдером.

Сайт требует ровно два изображения и передаёт их упорядоченный список через
общий видеоввод. Локальный владелец может включить группу отдельно:
`SYNTX_OWNER_KLING_KEYFRAMES=1` в owner-stdio контуре. По умолчанию группа
выключена; в обычный и HTTP-серверы она автоматически не добавляется.
Раньше этот флаг открывал только подготовку изображений; теперь он включает
и команды платной генерации. Сам запуск MCP ничего не генерирует — требуется
отдельный вызов инструмента.

Подготовку входов выполняют `syntx_owner_get_kling_keyframes_input_policy`,
`syntx_owner_upload_kling_keyframes_image` и
`syntx_owner_check_kling_keyframes_images`. Загрузите два файла с явными
`link_attempt_id`, `content_base64`, `filename`, `mime_type`, затем передайте
их `image_handles` проверке в нужном порядке. Возвращаются непрозрачные
ссылки-идентификаторы и метаданные без приватных URL или данных владельца.
Идентификаторы действуют 15 минут и привязаны к текущему входу; отзыв входа
их аннулирует. Два файла с одинаковыми байтами и разными именами допускаются.
При `UPLOAD_OUTCOME_UNKNOWN` загрузка автоматически не повторяется.

Для работы с заданиями добавлены ещё пять инструментов:

- `syntx_get_kling_keyframes_parameters` — настройки и границы их проверки;
- `syntx_owner_generate_kling_keyframes` — одна отправка с двумя изображениями;
- `syntx_owner_reconcile_kling_keyframes` — получение результата через GET без повторной генерации;
- `syntx_owner_list_kling_keyframes_recoveries` — список заданий текущего входа;
- `syntx_owner_get_kling_keyframes_result_page` — страница уже полученных результатов.

В генератор передаются `link_attempt_id`, два `image_handles` в нужном порядке,
непустой `prompt` и явные настройки из схемы инструмента. Перед отправкой
проверяются текущий вход, подписка, доступ к модели и доступная оценка стоимости.
Эта оценка не устанавливает верхний предел списания: `cost_cap_enforced=false`.
Входы передаются как два объекта изображения, без придуманных ролей кадров.
Их порядок сохранён, но интерпретация первого и последнего кадра провайдером
этим не доказывается. Число выходных видео не выводится из числа входов.

При `OUTCOME_UNKNOWN` сохраните `recovery_id` и используйте только reconcile:
повторный generate не является безопасным способом ожидания. Потерянное
подтверждение ищется в истории по единственному точному совпадению своего
запроса; неоднозначность остаётся неопределённым результатом. Получение видео
возможно после истечения 15 минут входных ссылок, пока действует тот же вход
и работает процесс MCP. Состояние заданий и защита от повтора не переживают
перезапуск; перед ним сохраните результаты. Перезапуск не делает безопасным
повтор запроса с неопределённым исходом. Отзыв входа закрывает доступ к ним.
Reconcile заново читает историю и результаты, даже если ранее уже были
доступны видео. Это позволяет получить дополнительные файлы того же задания.
Добавление файлов допускается только при сохранении всех прежних идентификаторов
и порядка; подмена или сокращение набора не принимаются. Счётчик
`diagnostic.history_get_calls` учитывает отдельные прочитанные страницы.

Проверки используют настоящие классы и MCP SDK с синтетическим HTTP.
Новая генерация на живом аккаунте, поддержка каждого сочетания у провайдера
и окончательный статус его задания этим выпуском не подтверждены.

В библиотечном API также есть явная проверка настроек и построитель шаблона
`buildOwnerKlingKeyframesWireSettingsTemplate({ parameters, controls })`.
Текущие значения версии: `1.5`, `1.6`, `2.1`, `2.5`, `2.6`, `3.0`;
`2.5-turbo` не подменяется автоматически на `2.5`. До 3.0 доступны `hd` и
5 либо 10 секунд, включая версию 2.1; в 3.0 — `standart`, `hd`, `4K` и
целые 3–15 секунд. Камера с шестью осями и четырьмя пресетами проверяется
отдельно только для 1.5 HD. Температура указывается явно: 0–1, шаг 0.1;
для 3.0 обязателен явный `multi_shots`. Непустой текст запроса обязателен
для всех шести версий; локальные ограничения его длины не являются
подтверждённым пределом провайдера.

`aspect_ratio` нужно выбрать явно: `16:9`, `1:1`, `9:16` или
`null` для отсутствующего поля. Это локальная политика явной проекции,
не обещание поддержки пропорций провайдером и не восстановление скрытого
состояния интерфейса. Шаблон не подставляет неизвестные значения по умолчанию,
не содержит файлов или промпта и не отправляет платный запрос.

### Kling Motion Control: видео с собственным роликом или пресетом

Motion Control доступен только в явно включённом owner-stdio контуре через
`SYNTX_OWNER_KLING_MOTION_CONTROL=1`. Для подготовки видео нужно задать
`SYNTX_OWNER_KLING_MOTION_CONTROL_FFPROBE_PATH` — абсолютный путь к доверенному
исполняемому файлу `ffprobe`. Установите бинарник самостоятельно и проверьте,
что это нужный вам executable. Команда `syntx-mcp-media-config` показывает
пример конфигурации только после `--confirm-enable-paid-tools`; она не меняет
настройки клиента, не читает учётные данные и не запускает генерацию. Полученную
JSON-конфигурацию нужно перенести в настройки клиента и заменить placeholder
абсолютным путём к выбранному исполняемому файлу.

Команду запускайте из корня клонированного репозитория:

```sh
node scripts/print-media-mcp-config.mjs --confirm-enable-paid-tools
```

Группа содержит девять инструментов:

- `syntx_owner_get_kling_motion_control_parameters` — закреплённые варианты и локальные ограничения;
- `syntx_owner_upload_kling_motion_control_image` и `syntx_owner_upload_kling_motion_control_video` — загрузка собственных входов;
- `syntx_owner_list_kling_motion_control_presets` и `syntx_owner_select_kling_motion_control_preset` — просмотр доступных пресетов и выбор аудио- или безаудио-варианта;
- `syntx_owner_generate_kling_motion_control_video` — один явный запрос генерации;
- `syntx_owner_reconcile_kling_motion_control_video`, `syntx_owner_list_kling_motion_control_recoveries` и `syntx_owner_get_kling_motion_control_result_page` — чтение и восстановление уже запущенного задания.

Для запроса задаются версия `2.6` или `3.0`, режим `standart` или `hd`, тип
`mcv` или `mci`, `native_audio` и целая длительность в секундах. Локальный
предел длительности — 3–30 секунд для `mcv` и 3–10 для `mci`; фактическое
поддерживаемое сочетание у провайдера этим не подтверждается. Значения по
умолчанию неизвестны, поэтому параметры передаются явно. Стоимость проверяется
по пяти ключам: `mode`, `video_duration`, `version`, `native_audio` и
`gen_type`. Это не гарантирует цену или ограничение списания:
`cost_cap_enforced=false`.

Можно передать пару собственных `image_handle` и `video_handle` либо выбрать
пресет, получить `preset_video_handle` и использовать его вместе с собственным
изображением. Ссылки в результатах каталога пресетов имеют только локальную
оценку происхождения по разрешённому R2-origin; это не подтверждает их
провайдером. Изображения принимаются в JPEG, PNG, AVIF или WebP и должны иметь
стороны не меньше 300 пикселей; локальный предел — 64 MiB, а размерный предел
источника каталога неизвестен. Видео принимается как MP4 или MOV, со сторонами
от 300 пикселей, длительностью 3–30 секунд и локальным пределом 100 MiB;
верхний предел размера источником каталога также неизвестен.
Для выбранного режима `mci` исходный ролик также ограничен десятью секундами.
Верхняя граница размера кадра источником не задана. `ffprobe` должен определить
явную допустимую SDR transfer characteristic; отсутствие или неизвестное
значение не принимается. Метаданные проверяются локально, но файлы не
декодируются для проверки каждого пикселя. Prompt необязателен; пустая строка
допускается.

Генерацию запускает только явный вызов инструмента; он может повлечь расходы.
Если ответ после отправки потерян, сохраните `recovery_id` и используйте
reconcile или чтение результата — повторный вызов generate не является
безопасным способом ожидания. Защита от повтора и recovery-записи существуют
только в текущем процессе MCP; перезапуск их не сохраняет. Подписка и доступ
проверяются перед чатом и повторно перед отправкой. Просроченная подписка
блокирует запрос; покупка или обход этого ограничения не выполняются.

Проверка проводится локально на синтетических HTTP-ответах с настоящими
классами и MCP SDK. Она не доказывает live-поведение API, подтверждение
генерации провайдером, все комбинации настроек, поддержку всех пресетов,
сохранность recovery после перезапуска, поддержку всех клиентских хостов или
полный каталог моделей.

### Suno: ссылки на собственные треки

Suno opt-in `SYNTX_OWNER_SUNO_GENERATION=1` дополнительно включает read-only
команду `syntx_owner_list_suno_track_inputs` для уже прочитанных результатов
своей текущей generation/recovery-попытки:

```json
{
  "link_attempt_id": "link_0123456789abcdef0123",
  "recovery_id": "suno_generation_recovery_01234567-89ab-4cde-8fab-0123456789ab"
}
```

Идентификаторы примера вымышлены. Ответ содержит `recovery_id`,
`status` (`AVAILABLE` или `UNAVAILABLE`) и `tracks` с полями
`track_handle`, `model_id` (`V6`/`V6_wild`) и `expires_in_seconds`.
Фиксированные причины отсутствия: `TRACK_METADATA_UNAVAILABLE` или
`TRACK_INPUT_CAPACITY_REACHED`; при частичном списке возможна отметка лимита.
Нет raw clip/task/chat/message IDs, URLs, prompt, principal или credentials.

Ссылки process-local, стандартный TTL 15 минут, предел хранилища 128.
Повторное чтение сохраняет ссылку до истечения TTL; затем она может быть
перевыдана из того же наблюдаемого owner-bound контекста. Чтение не вызывает
HTTP, account/cost reads, генерацию или платный повтор. Чужой, отозванный или
закрытый контекст недоступен. Рестарт теряет ссылки; это не durable recovery.
Команда не импортирует старые чаты и сама не выполняет генерацию.

### Готовые Suno-треки после нового входа

При том же флаге доступна `syntx_owner_list_existing_suno_tracks`:

```json
{"link_attempt_id":"link_0123456789abcdef0123","page":1}
```

Идентификатор вымышленный. Команда читает одну страницу собственного аудио-
индекса и проверяет историю и результаты распознанных чатов, ранее созданных
этим MCP. Это не полный браузер всех треков, созданных через сайт.
Она возвращает `track_handle`, `model_id`, `expires_in_seconds` и связанный
именно с этим треком `artifact` (`url`, `mime_type`). Полученную ссылку можно
передать существующим Cover/Extend без новой генерации основы.

Вход: текущий `link_attempt_id`, необязательная `page` (1–100, по умолчанию 1).
Ответ: `status`, `page`, `page_size` (20 чатов), `total_count`, `total_pages`,
`has_next`, `has_previous`, `tracks`; при пустом или ограниченном списке —
`unavailable_reason`: `NO_TRACKS_AVAILABLE` или `TRACK_INPUT_CAPACITY_REACHED`.
Поля общего числа относятся к чатам индекса, не к числу пригодных треков.
Список содержит не более 128 краткоживущих ссылок; наличие следующей страницы
не означает, что она уже прочитана. Длительность аудио не заявляется.

Чтение делает только ограниченные GET: без загрузки, генерации, проверки
баланса или стоимости. Provider IDs, clip/task metadata и исходные промпты
не возвращаются. После рестарта выполняется новый вход и новое чтение;
сами ссылки по-прежнему process-local, это не durable recovery.

### Suno Cover/Extend — экспериментальная группа

При том же `SYNTX_OWNER_SUNO_GENERATION=1` доступны шесть новых команд:

- `syntx_get_suno_track_operation_parameters`;
- `syntx_owner_cover_suno_audio`;
- `syntx_owner_extend_suno_audio`;
- `syntx_owner_reconcile_suno_track_operation`;
- `syntx_owner_list_suno_track_operation_recoveries`;
- `syntx_owner_get_suno_track_operation_result_page`.

Получите `track_handle` из результата текущей генерации через
`syntx_owner_list_suno_track_inputs` либо из проверенного готового трека через
`syntx_owner_list_existing_suno_tracks`. Cover и Extend
принимают `link_attempt_id`, `model_id` (`V6`/`V6_wild`),
`track_handle`, `prompt`, `is_custom_mode`, `is_instrumental`,
`negative_tags`, `styles` и `title`. Extend дополнительно требует
`continue_at` в секундах с шагом 0.1; Cover это поле отклоняет.
Операцию задаёт имя инструмента, поле `mode` передавать не нужно.
Модель должна совпадать с моделью исходного трека. Provider clip/task IDs,
URL, стоимость и source-пины во входе не принимаются.

Сохраняются TTL исходной ссылки, свежая проверка собственного доступа/тарифа,
одноразовый POST и GET-only recovery. Верхнюю границу `continue_at` по
длительности исходного файла сервис пока самостоятельно не проверяет.
После UNKNOWN запрос не повторяйте. `UPSTREAM_OPERATION_ERROR` означает
наблюдавшийся объект ошибки SYNTX, а не подтверждение статуса провайдера,
списания или возврата. Смешанные ответы сохраняют доступное аудио как
`partial_results`.

В одном разрешённом V6 Cover-пилоте получены, скачаны и полностью декодированы
два MP3. V6 Extend-пилот вернул два объекта ошибки SYNTX без аудио; конкретная
причина не подтверждена. После наблюдения дополнительно выровнено фиксированное
пустое `file_urls: []` с формой сайта; это не доказывает причину той ошибки.
В отдельном V6_wild Cover-пилоте также получены, скачаны и полностью
декодированы два MP3. Отдельный V6_wild Extend на отметке 35 секунд дал
два объекта ошибки SYNTX без аудио; причина не подтверждена, запрос не повторяли.
Поэтому группа экспериментальная; полнота всех моделей и настроек не заявляется.

17 октября новый отдельный MCP Extend на свежем собственном существующем V6
треке (`continue_at=0`) прошёл account/access/affordability. Отправлены один чат
и один POST, без upload или новой генерации основы. После `OUTCOME_UNKNOWN`

Причина, provider terminal и списание/возврат неизвестны; запрос не повторялся.

(references, edit/inpaint и upscale), а также отдельных WAN/Luma/Hailuo video и

Некоторые параметры остаются source-only или явно недопущены к запуску.

Это не покрытие всех моделей или всех комбинаций controls. Локальные тесты и
отдельные UI/provider observations не доказывают доступность, стоимость или

### Диагностика ожидания видео

При включении хотя бы одного reviewed no-reference видео-сервиса сервер
добавляет один read-only инструмент `syntx_owner_get_video_recovery_diagnostic`.
Без этих сервисов инструмент отсутствует. Он принимает только

```json
{
  "model_id": "hailuo-01-live",
  "link_attempt_id": "link_0123456789abcdef0123",
  "recovery_id": "recovery_01234567-89ab-4cde-8fab-0123456789ab"
}
```

Идентификаторы в примере вымышлены. Реальные ссылки выдаются текущим процессом
для собственной связанной попытки. Поддерживаемые маршруты: Hailuo
`hailuo-01`, `hailuo-01-director`, `hailuo-02`, `hailuo-2.3`,
`hailuo-01-live`; Seedance `seedance-2.0`; Kling `kling_text2video`,
`kling_o1_text2video`; Veo `veo3`, `veo3fast`, `veo3fast_r`; Grok
`grok_t2v`. Доступны только реально включённые сервисы; Kling/Veo привязывают
точную модель, а не ищут запись в соседних engine.

Ответ `{model_id, diagnostic}` содержит фиксированные локальные фазы,
наблюдения подтверждения/истории/результата и GET-счётчики
`poll_usage` с `count` (максимум 256) и `capped`. Это не статус принятия
или завершения задачи провайдером. Нет prompt, URL, аккаунта, credentials
или произвольного текста ошибок. Чужие, отозванные и истёкшие handles недоступны.

Чтение не вызывает HTTP, account/cost reads, генерацию, повторную отправку или
отмену. Recovery остаётся process-local: после закрытия/рестарта потерянную
попытку этот инструмент не восстановит. Не повторяйте UNKNOWN-генерации.

Video2Audio имеет шесть MCP-команд для загрузки, генерации и GET-only
восстановления. Исправлены оставшийся TTL handle и чтение новых метаданных
истории/точного префикса подтверждения. Получен один реальный MP4 со звуком;
чтение этого результата использовало совместимый GET-only слой тестового
сценария для уже запущенного старого процесса. Это отдельное наблюдение,
а не проверка установленного пакета во всех клиентах. Не повторяйте загрузку
или генерацию с неизвестным исходом; recovery пока остаётся process-local.

Opt-in `SYNTX_OWNER_SEEDANCE20_T2V=1` добавляет четыре команды Seedance 2.0
mini без references: 480p/720p, шесть соотношений сторон, 4–15 секунд и явный
переключатель звука. `mode=mini` задаёт сервер; скрытый `camera_fixed` не
отправляется. Пять source-bound полей preflight отделены от generation POST:
служебные `duration=0` и `size=aspect_ratio` не становятся настройками видео.
Другие режимы, references, defaults и гарантии стоимости здесь не заявлены.

В этом снимке исходников локально интегрированы opt-in профили Kling T2V,
Veo T2V и Grok T2V. Их локальные целевые проверки пройдены; это не доказывает
поддержку всех моделей или сочетаний настроек.

Kling T2V включает `kling_text2video` с версиями 1.5, 1.6,
2.1-master, 2.5-turbo, 2.6, 3.0 и 3.0-turbo, а также отдельную модель

## Требования и локальная проверка

Нужен Node.js **22.13.0 или новее**. Рекомендуемая и проверенная среда проекта —
**Node.js 24.21.0**.

Полный developer suite и проверки установленного SDK-пакета требуют именно
**24.21.0**. Матрица Node 22.13.0 отдельно проверяет сборку, конфигурацию и
инициализацию MCP; она не подменяет закреплённые Node 24 SDK-проверки.

Для полного developer test suite нужен также Gitleaks 8.30.1; в Linux CI он
устанавливается из официального release с проверкой закреплённого SHA-256.
Для обычного запуска MCP этот сканер не нужен.

На Linux для полного suite задайте `TMPDIR` на отдельную приватную папку вне
checkout, с правами 0700 и безопасными родительскими каталогами. Общий `/tmp`
не подходит для тестов защищённого профиля: его права не нужно ослаблять или
менять. GitHub workflow готовит такую папку сам. Синтетические тесты не
используют личные аккаунты. `.gitattributes` сохраняет LF при Windows checkout,
чтобы переносы строк не нарушали контрольные суммы версионируемого каталога.

```sh
git clone https://github.com/alexfisenkov/syntx-mcp.git
cd syntx-mcp
npm ci
npm run typecheck
npm test
```

`npm test` включает сборку и публичный synthetic test suite. Тесты, которым
нужны нераспространяемые приватные исторические подтверждения, в снимок не
входят; это не результат полного внутреннего набора. Для отдельной сборки:

```sh
npm run build
```

Проверка чистого устанавливаемого пакета:

```sh
npm run package:cache:prime -- --confirm-registry-fetch
npm run package:smoke:public
```

Первая команда отдельно получает метаданные и архивы закреплённых зависимостей
из официального npm registry, подготавливая кэш; она не вызывает SYNTX,
Telegram или генерации и не меняет исходники/lockfile. Без точного флага она
ничего не устанавливает. Вторая команда остаётся строго офлайн: одного
`npm ci` в свежем кэше для этой проверки недостаточно.

Она проверяет manifest, отсутствие приватных данных и реальные синтетические
SDK-сценарии установленного пакета. Старые личные provider-proof помечаются
`NOT_DISTRIBUTED`, а не подменяются фиктивными подтверждениями.

Workflow GitHub Actions запускается вручную без аккаунтов и secrets. По
умолчанию он проверяет только изменённое media-покрытие на Linux/Node 24.21.0:
build, целевые synthetic tests, public manifest/read-safety и Gitleaks. Полная
portability-матрица Ubuntu, macOS и Windows на Node 22.13.0 и 24.21.0, включая
полный suite на Ubuntu/24.21.0, запускается отдельным выбором `full`.
Synthetic tests не должны выполнять загрузки или генерацию. Историческая
матрица подтверждает stdio build/config/startup на шести сочетаниях ОС и Node;
она не подтверждает приёмку всех MCP-клиентов. Поддержка stdio в серверном
процессе не равна готовому HTTPS deployment: hosted HTTPS и проверка реальных
клиентов остаются отдельными задачами.

### WAN 2.6 R2V: локальный owner MCP-путь

В исходном коде предусмотрены восемь инструментов для wan_26_r2v и
wan_26_r2v_flash: чтение параметров, загрузка изображения и выбранного

точный GET-only reconcile, список process-local recoveries и чтение страницы
уже наблюдавшихся результатов. Runtime/stdio интеграция прошла шесть
source-level synthetic checks; config helper прошёл одну проверку. Это не
проверка чистой установки пакета и не доказательство успешной live-генерации.

Предусмотрено локальное включение через SYNTX_OWNER_WAN26_R2V=1 и доверенные
абсолютные пути SYNTX_OWNER_WAN26_R2V_FFPROBE_PATH и
SYNTX_OWNER_WAN26_R2V_FFMPEG_PATH. По умолчанию группа выключена и
предназначена для owner stdio. Нужен обычный per-user login; HTTP/HTTPS/cloud

у Flash. Handles привязаны к owner attempt/model и

не проецируются. Controls нужно передавать явно. Локальные resource guards не
являются provider limits. Неопределённую генерацию нельзя повторять:
используйте только точный GET-only reconcile. Provider acceptance, terminal
status, фактическая цена и списание не подтверждены; жёсткого cost cap нет.

проверки не дали. В отдельном live-пилоте Flash обычный login и загрузка одного
синтетического изображения прошли, но единственная генерация вернула
OUTCOME_UNKNOWN. Три GET-запроса того же recovery не получили ACK или результат;
сессия закрыта без дополнительных генераций. Причина, provider terminal status

refund или неотправку. Regular-модель live-пилотом не проверялась.

В обновлённой диагностике поле diagnostic.start_error_class nullable и содержит
только allowlisted-категорию локальной ошибки HTTP-клиента; само поле не
содержит raw error, body, URL, IDs или secrets. Значение сохраняется через GET
recovery, включая completed результат. Для старых TS DTO поле может
отсутствовать или быть null; текущий MCP DTO возвращает null либо значение из
закрытого списка.
Оно не определяет точный HTTP status, причину Flash-пилота, provider terminal
status или billing и не разрешает повторную генерацию.

Owner media — только локальный stdio-путь. По умолчанию эти платные инструменты
выключены. После сборки helper может вывести пример конфигурации:

```sh
npm run build
node scripts/print-media-mcp-config.mjs --confirm-enable-paid-tools
```

Точный флаг подтверждает только печать конфигурации: скрипт не меняет файлы
клиента, не читает секреты и не начинает генерацию. Полученный JSON включает
набор owner media flags; перед использованием отредактируйте его и оставьте
включёнными только нужные группы. Сами инструменты при вызове могут расходовать
баланс или подписку SYNTX. Не передавайте токены, cookies или Telegram-сессию в
поля MCP.

Каждый пользователь связывает собственную SYNTX-учётную запись через обычный
одноразовый Telegram handoff сервера; подтверждение можно выполнить вручную в
своём Telegram. Не используется общая сессия или общий API credential.
Необязательный отдельный Telegram companion:
[telegram-mcp-starter](https://github.com/alexfisenkov/telegram-mcp-starter).
Он не требуется для обычного ручного подтверждения и не должен подключать
чужой аккаунт или создавать в этом проекте личную MTProto-сессию владельца.

Транспорт с owner media — **stdio**. HTTP owner surface ограничена loopback и
не предназначена для публикации в интернете; HTTPS deployment ещё не включён.

## Безопасное восстановление

После timeout или неопределённого результата не отправляйте ту же платную
генерацию повторно. Если конкретная группа предоставляет reconciliation или
recovery tool, используйте только её GET-путь и исходную попытку. Часть
восстановления остаётся process-local и может не пережить перезапуск.
