# SYNTX MCP — alpha

Публичный исходный проект MCP-сервера для каталога SYNTX AI, per-user account
linking и некоторых явно описанных image, video и audio flows. Это ранняя
разработка, а не полный клиент SYNTX и не обещание совместимости со всеми
моделями, настройками или MCP-хостами.

## Покрытие и ограничения

### Speech-to-Speech и Topaz: текущая разработка

STS имеет восемь MCP-команд в owner-stdio контуре:

- `syntx_get_elevenlabs_sts_parameters`;
- `syntx_owner_upload_elevenlabs_sts_original`;
- `syntx_owner_generate_elevenlabs_sts`;
- `syntx_owner_reconcile_elevenlabs_sts`;
- `syntx_owner_list_elevenlabs_sts_recoveries`;
- `syntx_owner_get_elevenlabs_sts_result_page`;
- `syntx_owner_list_existing_elevenlabs_sts_results`;
- `syntx_owner_get_existing_elevenlabs_sts_result`.

Включение по умолчанию выключено. Оператор задаёт `SYNTX_OWNER_ELEVENLABS_STS=1`,
`SYNTX_OWNER_ELEVENLABS_STS_FFPROBE_PATH` — абсолютный путь к установленному
`ffprobe`, и `SYNTX_OWNER_ELEVENLABS_STS_UPLOAD_DESTINATION` — явно `uploaded`
или `hidden`. Назначение не выбирается автоматически. Обычный HTTP-сервер
эту операцию не включает.

Войдите через обычный Telegram flow. Команда общего списка голосов
`syntx_owner_list_elevenlabs_voice_references` возвращает доступные ссылки
`voice_ref`. Upload принимает `link_attempt_id`, `filename` с расширением
`.mp3`, `mime_type: "audio/mpeg"`, `content_base64` и возвращает
`audio_original_handle`. Generate принимает тот же `link_attempt_id`,
`model_id: "eleven_multilingual_sts_v2"`, `mode: "speech_to_speech"`,
`audio_original_handle` и выбранный `voice_ref`. Длительность измеряется
сервером, а пустой prompt и typed audio reference формируются внутри MCP.

При `OUTCOME_UNKNOWN` не повторяйте генерацию: получите существующий
`recovery_id` через список восстановлений и вызовите reconcile. Результат
содержит `artifacts[].object_url`. Состояние process-local; перезапуск теряет
его. Перед запуском читаются свежие подписка, доступ и конечная оценка цены;
`cost_cap_enforced: false` означает отсутствие жёсткой гарантии списания.

После нового входа отдельный GET-only список существующих STS-результатов
принимает `link_attempt_id` и `page` (по 20 чатов). Он возвращает короткоживущие
непрозрачные `result_handle`; команда получения принимает такой handle и
повторно проверяет текущего владельца, историю, модель и точный аудиообъект.
Загрузка и генерация при этом не запускаются. Поддерживается только узнаваемая
история STS-чата, созданного этим MCP. Исходный файл и fingerprint прежнего
запроса после перезапуска не восстанавливаются: `source_provenance: NOT_AVAILABLE`.

Фактический MCP-пилот подтвердил обычный вход, одну загрузку нового MP3,
одну генерацию и получение одного аудиорезультата через GET-only recovery.
Первое ожидание было неопределённым. Сессия закрыта, повторного POST не было.
Независимое декодирование нового файла не подтверждено: приватный валидатор
скачивания ошибочно требовал duration из MP3-потока; файл не был сохранён.
Это не доказательство терминального статуса провайдера, возврата оплаты,
качества голоса или совместимости со всеми MCP-хостами.

Ниже — отдельные границы исходников и Topaz.

Добавлены локальные основы STS: измерение MP3 через доверенный `ffprobe`,
отдельная загрузка до 50 MiB, ссылка на аудио владельца, подготовка пустого
промпта с типизированным аудиовложением и защита от повторного запуска.
Длительность берётся из файла и округляется по текущей форме сайта.
Один веб-кейс смены голоса вернул связанный с запросом MP3, который скачан
и полностью декодирован. Это отдельный веб-кейс, не файл нового MCP-пилота.
Конкретная WAV-загрузка была отклонена; широкая поддержка WAV не заявляется.

Topaz Astra добавляет шесть owner-stdio команд:

- `syntx_get_topaz_astra_parameters`;
- `syntx_owner_upload_topaz_astra_original`;
- `syntx_owner_generate_topaz_astra`;
- `syntx_owner_reconcile_topaz_astra`;
- `syntx_owner_list_topaz_astra_recoveries`;
- `syntx_owner_get_topaz_astra_result_page`.

Для включения оператор задаёт `SYNTX_OWNER_TOPAZ_ASTRA=1`, абсолютный
`SYNTX_OWNER_TOPAZ_ASTRA_FFPROBE_PATH` и явный
`SYNTX_OWNER_TOPAZ_ASTRA_UPLOAD_DESTINATION=uploaded` либо `hidden`.
По умолчанию группа выключена; обычный HTTP-сервер её не включает.
Upload принимает `link_attempt_id`, `model_id`, `filename`, `mime_type`
(`video/mp4` либо `video/quicktime`) и `content_base64`. Возвращённый
`topaz_original_handle` используется в generate вместе с тем же входом,
`model_id`, необязательным `prompt` и явными `parameters`: `resolution`
(`1920x1080`/`3840x2160`), `frame_rate` (24/30/60/120), `slowmo`
(null/2/3/4/6/8/10/12/16), `creativity` (`low`/`middle`/`high`).

Поддержаны исходные профили `slc-1`, `slf-2`, `slp-2`, `slp-2.5`.
Поле `creativity` отправляется только для `slc-1`/`slp-2.5`.
Длительность измеряется из видео; в wire используется объект разрешения,
а не строка, и отсутствует обычное поле `n`. Цена проверяется отдельно.
При неопределённом результате не повторяйте generate: используйте
`recovery_id` для GET-only reconcile и чтения результатов.
Защита от повтора и recovery пока process-local, не переживают перезапуск.

Реальные классы и официальный MCP SDK проверены на синтетической цепочке
«загрузка → один POST генерации → результат». Новая генерация Topaz на
живом провайдере, фактические списания и все сочетания настроек не проверены.
Это не гарантия провайдерской совместимости; `cost_cap_enforced: false`.
Точные границы задают
[параметры STS](src/application/owner-elevenlabs-sts-parameters.ts) и
[профиль Topaz](src/application/owner-topaz-astra-source-profile.ts).

Для Hailuo-02 Image-to-Video добавлены исходные параметры, проверка контейнера
изображения, фиксированная загрузка и пользовательские handles. Генерация
I2V через MCP ещё не подключена. Местный предел изображения 10 MiB не является
подтверждённым ограничением провайдера и не заменяет полное декодирование.

Suno Cover имеет подтверждённые MP3-результаты для V6/V6_wild. Две попытки
Extend дали общие ошибки; причину не удалось подтвердить. Текущее меню
просмотренного трека предлагает только Cover. Это не вывод о глобальном
отсутствии Extend; старые неопределённые запросы не повторяются.

### Чтение загруженных файлов

Чтение загруженных файлов использует отдельный предел ответа 256 KiB:
он позволяет прочитать страницу до 100 записей с расширенными метаданными.
Остальные JSON-запросы сохраняют предел 64 KiB. Явно заданный оператором
`maxResponseBytes` по-прежнему ограничивает оба режима. Внешние URL и hash
из списка файлов не возвращаются в публичных результатах этого инструмента.
Этот предел не означает поддержку скачивания или восстановления image handle.

### Kling Image-to-Video

Opt-in `SYNTX_OWNER_KLING_I2V=1` добавляет пять инструментов:

- `syntx_owner_get_kling_i2v_parameters`;
- `syntx_owner_upload_kling_i2v_image`;
- `syntx_owner_generate_kling_i2v_video`;
- `syntx_owner_reconcile_kling_i2v_video`;
- `syntx_owner_list_kling_i2v_recoveries`.

Войдите обычным способом через Telegram, загрузите собственное изображение
и передайте полученный `image_handle` в генерацию. Загрузка принимает
`link_attempt_id`, `content_base64`, `filename` и `mime_type`.
JPEG/JPG, PNG, WebP и AVIF ограничены 30 MiB; обе стороны по метаданным
контейнера должны быть не меньше 300 пикселей. Это не полная проверка декодирования
изображения. Используется `destination=uploaded`, как в обычном видеовводе
сайта. SHA-256 возвращается как 64 hex-символа без префикса; исправлена
несогласованность между ответом сервиса и схемой MCP. URL файла и provider IDs
не возвращаются.

Генерация принимает `link_attempt_id`, `image_handle`,
`model_id: "kling_image2video"`, `prompt`, `version`, `mode`,
`video_duration`, `native_audio` и `temperature`.
Версии: 1.5, 1.6, 2.1-master, 2.5-turbo, 2.6, 3.0 и 3.0-turbo.
Температура задаётся явно во всех версиях: 0–1 с шагом 0.1, даже если сайт
скрывает этот контроль. Версия 3.0 дополнительно требует `multi_shots: false`;
сцены и `multi_shots: true` пока не поддержаны.
Допустимые сочетания режимов, длительности и аудио проверяет схема инструмента;
версия 3.0-turbo позволяет не передавать промпт.

Перед единственным POST читаются свежие тариф, доступ к модели и конечная
оценка стоимости. Оценка не является гарантией списания или верхним лимитом.
Результат содержит непрозрачный `recovery_id` и проверенные ссылки на видео.
При `OUTCOME_UNKNOWN` не повторяйте генерацию: используйте GET-only сверку
с теми же `link_attempt_id` и `recovery_id`.

Ссылки на изображения действуют 15 минут и привязаны к текущему аккаунту;
получение уже запущенного результата не требует продлевать ссылку изображения.
Восстановление после перезапуска процесса пока не реализовано.
Пять инструментов доступны только в явно включённом owner-stdio контуре;
обычный и HTTP-серверы их автоматически не включают.
Сквозная проверка через MCP подтвердила обычный вход, чтение доступа, загрузку
нового JPEG, генерацию и получение одного реального MP4: версия 2.6,
`mode=hd`, 5 секунд, `native_audio=false`, `temperature=0.5`. Видео H.264
1920×1080 скачано и полностью декодировано. Первое ожидание вернуло
`OUTCOME_UNKNOWN`; GET-only сверка получила результат без повторного POST.
Сессия закрыта. Это доказательство указанного сочетания, а не всех версий,
параметров или клиентов. Старые неопределённые загрузки не повторялись.

Suno opt-in `SYNTX_OWNER_SUNO_GENERATION=1` дополнительно включает read-only
команду `syntx_owner_list_suno_track_inputs` для уже прочитанных результатов
своей текущей generation/recovery-попытки:

```json
{
  "link_attempt_id": "link_0123456789abcdef0123",
  "recovery_id": "suno_generation_recovery_01234567-89ab-4cde-8fab-0123456789ab"
}
```

Идентификаторы примера вымышлены. Ответ содержит `recovery_id`,
`status` (`AVAILABLE` или `UNAVAILABLE`) и `tracks` с полями
`track_handle`, `model_id` (`V6`/`V6_wild`) и `expires_in_seconds`.
Фиксированные причины отсутствия: `TRACK_METADATA_UNAVAILABLE` или
`TRACK_INPUT_CAPACITY_REACHED`; при частичном списке возможна отметка лимита.
Нет raw clip/task/chat/message IDs, URLs, prompt, principal или credentials.

Ссылки process-local, стандартный TTL 15 минут, предел хранилища 128.
Повторное чтение сохраняет ссылку до истечения TTL; затем она может быть
перевыдана из того же наблюдаемого owner-bound контекста. Чтение не вызывает
HTTP, account/cost reads, генерацию или платный повтор. Чужой, отозванный или
закрытый контекст недоступен. Рестарт теряет ссылки; это не durable recovery.
Команда не импортирует старые чаты и сама не выполняет генерацию.

### Готовые Suno-треки после нового входа

При том же флаге доступна `syntx_owner_list_existing_suno_tracks`:

```json
{"link_attempt_id":"link_0123456789abcdef0123","page":1}
```

Идентификатор вымышленный. Команда читает одну страницу собственного аудио-
индекса и проверяет историю и результаты распознанных чатов, ранее созданных
этим MCP. Это не полный браузер всех треков, созданных через сайт.
Она возвращает `track_handle`, `model_id`, `expires_in_seconds` и связанный
именно с этим треком `artifact` (`url`, `mime_type`). Полученную ссылку можно
передать существующим Cover/Extend без новой генерации основы.

Вход: текущий `link_attempt_id`, необязательная `page` (1–100, по умолчанию 1).
Ответ: `status`, `page`, `page_size` (20 чатов), `total_count`, `total_pages`,
`has_next`, `has_previous`, `tracks`; при пустом или ограниченном списке —
`unavailable_reason`: `NO_TRACKS_AVAILABLE` или `TRACK_INPUT_CAPACITY_REACHED`.
Поля общего числа относятся к чатам индекса, не к числу пригодных треков.
Список содержит не более 128 краткоживущих ссылок; наличие следующей страницы
не означает, что она уже прочитана. Длительность аудио не заявляется.

Чтение делает только ограниченные GET: без загрузки, генерации, проверки
баланса или стоимости. Provider IDs, clip/task metadata и исходные промпты
не возвращаются. После рестарта выполняется новый вход и новое чтение;
сами ссылки по-прежнему process-local, это не durable recovery.

### Suno Cover/Extend — экспериментальная группа

При том же `SYNTX_OWNER_SUNO_GENERATION=1` доступны шесть новых команд:

- `syntx_get_suno_track_operation_parameters`;
- `syntx_owner_cover_suno_audio`;
- `syntx_owner_extend_suno_audio`;
- `syntx_owner_reconcile_suno_track_operation`;
- `syntx_owner_list_suno_track_operation_recoveries`;
- `syntx_owner_get_suno_track_operation_result_page`.

Получите `track_handle` из результата текущей генерации через
`syntx_owner_list_suno_track_inputs` либо из проверенного готового трека через
`syntx_owner_list_existing_suno_tracks`. Cover и Extend
принимают `link_attempt_id`, `model_id` (`V6`/`V6_wild`),
`track_handle`, `prompt`, `is_custom_mode`, `is_instrumental`,
`negative_tags`, `styles` и `title`. Extend дополнительно требует
`continue_at` в секундах с шагом 0.1; Cover это поле отклоняет.
Операцию задаёт имя инструмента, поле `mode` передавать не нужно.
Модель должна совпадать с моделью исходного трека. Provider clip/task IDs,
URL, стоимость и source-пины во входе не принимаются.

Сохраняются TTL исходной ссылки, свежая проверка собственного доступа/тарифа,
одноразовый POST и GET-only recovery. Верхнюю границу `continue_at` по
длительности исходного файла сервис пока самостоятельно не проверяет.
После UNKNOWN запрос не повторяйте. `UPSTREAM_OPERATION_ERROR` означает
наблюдавшийся объект ошибки SYNTX, а не подтверждение статуса провайдера,
списания или возврата. Смешанные ответы сохраняют доступное аудио как
`partial_results`.

В одном разрешённом V6 Cover-пилоте получены, скачаны и полностью декодированы
два MP3. V6 Extend-пилот вернул два объекта ошибки SYNTX без аудио; конкретная
причина не подтверждена. После наблюдения дополнительно выровнено фиксированное
пустое `file_urls: []` с формой сайта; это не доказывает причину той ошибки.
В отдельном V6_wild Cover-пилоте также получены, скачаны и полностью
декодированы два MP3. Отдельный V6_wild Extend на отметке 35 секунд дал
два объекта ошибки SYNTX без аудио; причина не подтверждена, запрос не повторяли.
Поэтому группа экспериментальная; полнота всех моделей и настроек не заявляется.

В текущем наборе есть отдельные opt-in группы для выбранных image workflows
(references, edit/inpaint и upscale), а также отдельных WAN/Luma/Hailuo video и
ElevenLabs TTS/Suno audio workflows. Точные группы и настройки определяются
версиями исходников и опубликованными инструментами `tools/list`; наличие модели
в каталоге не означает, что каждое её поле или вариант доступен для dispatch.
Некоторые параметры остаются source-only или явно недопущены к запуску.

Дополнительно вводятся owner opt-in `SYNTX_OWNER_HAILUO02_T2V` для Hailuo 02
text-to-video (три пары; reference-input на 512 не включён) и
`SYNTX_OWNER_ELEVENLABS_DIALOGUE` для ElevenLabs dialogue (три модели в заданном
порядке, пять tools и один общий voice). Soul принимает необязательный
`reference_strength` только со значением `0.7`, если его передали явно. Defaults
и прежние payload сохраняются. Для Hailuo 02 получен один MP4, для ElevenLabs
dialogue — один MP3 от V4Turbo. Это подтверждает только эти два конкретных
результата, а не все модели, пары настроек или defaults.

Это не покрытие всех моделей или всех комбинаций controls. Локальные тесты и
отдельные UI/provider observations не доказывают доступность, стоимость или
приём каждого запроса; полноценная HTTPS-установка и restart-durable recovery
здесь не заявлены.

В исходном снимке есть экспериментальный opt-in
`SYNTX_OWNER_HAILUO_LIVE_T2V=1` для Hailuo-01 Live. Включение доступно в
локально проверенной конфигурации; оно не означает готовность провайдера к
полноценной работе. Профиль ограничен `hailuo-01-live`, `720p`, запросом на
6 секунд и отсутствием references. Поддержка необязательного изображения как
reference для Live не подтверждена.

В одном owner pilot были созданы чат и отправлен ровно один запрос генерации.
Ожидание и последующая GET-only сверка вернули неопределённый статус без
артефактов. Запрос не повторяли. Приём провайдером, успех или отказ не
подтверждены; HTTP-статус не был зафиксирован. Этот эксперимент не подтверждает
результат для Live, эффективные defaults, presets, другие настройки или модели.

### Диагностика ожидания видео

При включении хотя бы одного reviewed no-reference видео-сервиса сервер
добавляет один read-only инструмент `syntx_owner_get_video_recovery_diagnostic`.
Без этих сервисов инструмент отсутствует. Он принимает только

```json
{
  "model_id": "hailuo-01-live",
  "link_attempt_id": "link_0123456789abcdef0123",
  "recovery_id": "recovery_01234567-89ab-4cde-8fab-0123456789ab"
}
```

Идентификаторы в примере вымышлены. Реальные ссылки выдаются текущим процессом
для собственной связанной попытки. Поддерживаемые маршруты: Hailuo
`hailuo-01`, `hailuo-01-director`, `hailuo-02`, `hailuo-2.3`,
`hailuo-01-live`; Seedance `seedance-2.0`; Kling `kling_text2video`,
`kling_o1_text2video`; Veo `veo3`, `veo3fast`, `veo3fast_r`; Grok
`grok_t2v`. Доступны только реально включённые сервисы; Kling/Veo привязывают
точную модель, а не ищут запись в соседних engine.

Ответ `{model_id, diagnostic}` содержит фиксированные локальные фазы,
наблюдения подтверждения/истории/результата и GET-счётчики
`poll_usage` с `count` (максимум 256) и `capped`. Это не статус принятия
или завершения задачи провайдером. Нет prompt, URL, аккаунта, credentials
или произвольного текста ошибок. Чужие, отозванные и истёкшие handles недоступны.

Чтение не вызывает HTTP, account/cost reads, генерацию, повторную отправку или
отмену. Recovery остаётся process-local: после закрытия/рестарта потерянную
попытку этот инструмент не восстановит. Не повторяйте UNKNOWN-генерации.

Video2Audio имеет шесть MCP-команд для загрузки, генерации и GET-only
восстановления. Исправлены оставшийся TTL handle и чтение новых метаданных
истории/точного префикса подтверждения. Получен один реальный MP4 со звуком;
чтение этого результата использовало совместимый GET-only слой тестового
сценария для уже запущенного старого процесса. Это отдельное наблюдение,
а не проверка установленного пакета во всех клиентах. Не повторяйте загрузку
или генерацию с неизвестным исходом; recovery пока остаётся process-local.

Opt-in `SYNTX_OWNER_SEEDANCE20_T2V=1` добавляет четыре команды Seedance 2.0
mini без references: 480p/720p, шесть соотношений сторон, 4–15 секунд и явный
переключатель звука. `mode=mini` задаёт сервер; скрытый `camera_fixed` не
отправляется. Пять source-bound полей preflight отделены от generation POST:
служебные `duration=0` и `size=aspect_ratio` не становятся настройками видео.
Другие режимы, references, defaults и гарантии стоимости здесь не заявлены.

В этом снимке исходников локально интегрированы opt-in профили Kling T2V,
Veo T2V и Grok T2V. Их локальные целевые проверки пройдены; это не доказывает
поддержку всех моделей или сочетаний настроек.

Kling T2V включает `kling_text2video` с версиями 1.5, 1.6,
2.1-master, 2.5-turbo, 2.6, 3.0 и 3.0-turbo, а также отдельную модель
`kling_o1_text2video`: для O1 доступны только HD, соотношения 16:9, 1:1 и
9:16 и длительности 5 или 10 секунд. В базовой ветке первые пять версий
поддерживают 5 или 10 секунд, версии 3.0 и 3.0-turbo — от 1 до 15 секунд;
для 2.1-master доступен только HD. В обеих ветках референсы не принимаются.
Единственный подтверждённый запрос к провайдеру — Kling 1.5, `standart`,
16:9, запрос на 5 секунд без аудио; получен H.264-ролик 1280×720 длительностью
5,1 секунды.
Это не подтверждает остальные версии и сочетания настроек.

Veo T2V охватывает `veo3`, `veo3fast` и `veo3fast_r` в non-Omni ветке:
параметр качества принимает числовые значения 0, 1 или 2 (это не строки
`720p`, `1080p` или `4K`), соотношение сторон — 16:9 или 9:16, длительность —
8 секунд; референсы не принимаются. Подтверждён один результат: `veo3fast_r`,
числовое качество 0, 16:9, запрос на 8 секунд. Получен MP4 1280×720 длительностью
8,0 секунды со стерео AAC 48 кГц; полное декодирование прошло успешно. Это не
подтверждает другие модели, качества или настройки.

Для Grok T2V source-reviewed профиль `grok_t2v` описывает 480p/720p, пять
соотношений сторон (16:9, 9:16, 3:2, 2:3, 1:1), целые длительности 6–10
секунд и отсутствие reference-входов. Подтверждён один результат: `grok_t2v`,
480p, 16:9, запрос на 6 секунд. Получен MP4 с H.264 848×480 длительностью
6,041667 секунды и AAC stereo 44,1 кГц; полное декодирование прошло успешно.
Дополнительная встроенная MJPEG-миниатюра не является основным видеотреком.
Это не подтверждает другие модели или сочетания настроек.

Число строк в каталоге — не показатель полноты интеграций: архивы B066 и
выбранный snapshot E551 содержат по 200 model rows. Значение 198 относится к
отдельному raw current-models response, а не к числу строк этих архивов. Ни один
из этих наборов данных не означает поддержку всех моделей или их настроек.

## Требования и локальная проверка

Нужен Node.js **22.13.0 или новее**. Рекомендуемая и проверенная среда проекта —
**Node.js 24.21.0**.

Полный developer suite и проверки установленного SDK-пакета требуют именно
**24.21.0**. Матрица Node 22.13.0 отдельно проверяет сборку, конфигурацию и
инициализацию MCP; она не подменяет закреплённые Node 24 SDK-проверки.

Для полного developer test suite нужен также Gitleaks 8.30.1; в Linux CI он
устанавливается из официального release с проверкой закреплённого SHA-256.
Для обычного запуска MCP этот сканер не нужен.

На Linux для полного suite задайте `TMPDIR` на отдельную приватную папку вне
checkout, с правами 0700 и безопасными родительскими каталогами. Общий `/tmp`
не подходит для тестов защищённого профиля: его права не нужно ослаблять или
менять. GitHub workflow готовит такую папку сам. Синтетические тесты не
используют личные аккаунты. `.gitattributes` сохраняет LF при Windows checkout,
чтобы переносы строк не нарушали контрольные суммы версионируемого каталога.

```sh
git clone https://github.com/alexfisenkov/syntx-mcp.git
cd syntx-mcp
npm ci
npm run typecheck
npm test
```

`npm test` включает сборку и публичный synthetic test suite. Тесты, которым
нужны нераспространяемые приватные исторические подтверждения, в снимок не
входят; это не результат полного внутреннего набора. Для отдельной сборки:

```sh
npm run build
```

Проверка чистого устанавливаемого пакета:

```sh
npm run package:cache:prime -- --confirm-registry-fetch
npm run package:smoke:public
```

Первая команда отдельно получает метаданные и архивы закреплённых зависимостей
из официального npm registry, подготавливая кэш; она не вызывает SYNTX,
Telegram или генерации и не меняет исходники/lockfile. Без точного флага она
ничего не устанавливает. Вторая команда остаётся строго офлайн: одного
`npm ci` в свежем кэше для этой проверки недостаточно.

Она проверяет manifest, отсутствие приватных данных и реальные синтетические
SDK-сценарии установленного пакета. Старые личные provider-proof помечаются
`NOT_DISTRIBUTED`, а не подменяются фиктивными подтверждениями.

Workflow GitHub Actions запускается вручную без аккаунтов и secrets. По
умолчанию он проверяет только изменённое media-покрытие на Linux/Node 24.21.0:
build, целевые synthetic tests, public manifest/read-safety и Gitleaks. Полная
portability-матрица Ubuntu, macOS и Windows на Node 22.13.0 и 24.21.0, включая
полный suite на Ubuntu/24.21.0, запускается отдельным выбором `full`.
Synthetic tests не должны выполнять загрузки или генерацию. Историческая
матрица подтверждает stdio build/config/startup на шести сочетаниях ОС и Node;
она не подтверждает приёмку всех MCP-клиентов. Поддержка stdio в серверном
процессе не равна готовому HTTPS deployment: hosted HTTPS и проверка реальных
клиентов остаются отдельными задачами.

## Подключение owner media

Owner media — только локальный stdio-путь. По умолчанию эти платные инструменты
выключены. После сборки helper может вывести пример конфигурации:

```sh
npm run build
node scripts/print-media-mcp-config.mjs --confirm-enable-paid-tools
```

Точный флаг подтверждает только печать конфигурации: скрипт не меняет файлы
клиента, не читает секреты и не начинает генерацию. Полученный JSON включает
набор owner media flags; перед использованием отредактируйте его и оставьте
включёнными только нужные группы. Сами инструменты при вызове могут расходовать
баланс или подписку SYNTX. Не передавайте токены, cookies или Telegram-сессию в
поля MCP.

Каждый пользователь связывает собственную SYNTX-учётную запись через обычный
одноразовый Telegram handoff сервера; подтверждение можно выполнить вручную в
своём Telegram. Не используется общая сессия или общий API credential.
Необязательный отдельный Telegram companion:
[telegram-mcp-starter](https://github.com/alexfisenkov/telegram-mcp-starter).
Он не требуется для обычного ручного подтверждения и не должен подключать
чужой аккаунт или создавать в этом проекте личную MTProto-сессию владельца.

Транспорт с owner media — **stdio**. HTTP owner surface ограничена loopback и
не предназначена для публикации в интернете; HTTPS deployment ещё не включён.

## Безопасное восстановление

После timeout или неопределённого результата не отправляйте ту же платную
генерацию повторно. Если конкретная группа предоставляет reconciliation или
recovery tool, используйте только её GET-путь и исходную попытку. Часть
восстановления остаётся process-local и может не пережить перезапуск.
